## 一、批①:白名单分类门禁(四点)

### 1. 分类是否诚实 —— **不诚实,16 条里有 15 条归类错了**

Lead 的核心怀疑成立,而且比怀疑的更明确。

**实测判据**:一个模块若**除相对路径外无裸模块依赖**,Node 就能直接加载它 ——
它缺的只是一个 `import` 它的入口文件,那属于**欠账**;反之若依赖未安装的包,则**加载即失败**,属**结构不可能**。

```
node --input-type=module -e "import('<file:///…>')"
```

| 结果 | 数量 | 模块 |
| :--- | :---: | :--- |
| ✓ **能被 Node 直接加载**(只差入口) | **15** | `audio`、`stage/{assembly_math,dye_overlay,entity_sprites,iso_camera,particles,roof_transparency,shaders,tile_mesh}`、`ui/{blueprint,boss_hud,inventory,pixel_easel,recipe_tree,state_machine}` |
| ✗ 加载失败(依赖 `three`) | **1** | `three/stage_assembly.ts` → `ERR_MODULE_NOT_FOUND: Cannot find package 'three'` |

**关键对照证据**:

- `stage_assembly.ts` 明确注释「**唯一允许 import `three` 的地方**」,且 `package.json` 的 `dependencies` 为**空** ⇒ 本仓**结构上无法加载它**。
- 但那 15 个模块**一个外部包都不需要**。它们缺的是 `client/src/main.ts` 之类的入口 ——
  而 `client/` 目录**没有任何入口文件**(`main`/`index`/`app`/`boot`/`entry`/`game` 全部不存在),
  也**没有任何构建配置**(无 `vite`/`webpack`/`rollup`/`index.html`)。

**结论**:
- 16 条理由的**文字是真的**(本仓确实没有客户端入口)。
- 但把它们归入「**刻意不接**」(语义 = 不在本系统职责内)是**把欠账说成设计**。
- 准确分类应当是:**1 条「刻意不接」+ 15 条「待接线」**。

⇒ 真实的欠账是 **34 + 15 = 49 条**,不是 34 条。README 那行把 **49 说成了 34**。

**还有一个独立发现**:`stage_assembly.ts` 并非「刻意不接」,它**在台账里有未关闭待办**:

| 出处 | 条目 | 内容 |
| :--- | :--- | :--- |
| `WS-09-client-render.md:669` | **U1** | 「`stage_assembly.ts` 依赖 `three`,而仓库零依赖 — 该文件无法在测试中 import」→ 需要极简 three 相容层 |
| `EXTENDING.md:420` | **F7** | 「`client/src/three/stage_assembly.ts` 零引用 — 需要 `three` 才能跑」 |

⇒ 它被台账登记为**待办**,却被门禁分类为「刻意不接」——**同一份材料里两处口径相反**。
即便按「结构不可能」的最宽松解释,它也应是「待接线(等 three 相容层)」而非「刻意不接」。

### 3. 门禁是否有牙齿 —— **有牙齿;但发现第三种静默绕过(影子行)**

**独立复验**(自写脚本,不复用 Lead 的):

| 变体 | 退出码 | 结果 |
| :--- | :---: | :--- |
| 待接线 `34→33` | 1 | ✓ 抓到 |
| 刻意不接 `16→15` | 1 | ✓ 抓到 |
| 两数都改对 | 0 | ✓ 正确放行 |
| **整行删除** | 1 | ✓ 走「找不到」分支 |
| 全角数字 `３４` | 1 | ✓ 「找不到」 |
| 换措辞「待接线的有 34 条」 | 1 | ✓ 「找不到」 |
| 调换两数顺序 | 1 | ✓ 「找不到」 |
| 尾随空格 `34 ` | 0 | ✓ **不是绕过**——`Number('34')=34`,数字仍对 |
| 前导零 `034` | 0 | ✓ **不是绕过**——同上 |
| **影子行**(正确行在前、真行改错) | **0** | **✗ 静默放行** |
| **影子行藏进代码块** | **0** | **✗ 静默放行** |
| **影子行藏进 HTML 注释** | **0** | **✗ 静默放行** |

**根因**:`readmeText.match(...)` 只取**首个**匹配(`verify.ts:2400`)。

```ts
const wm = readmeText.match(/白名单构成:待接线\s*(\d+)\s*\/\s*刻意不接\s*(\d+)/);
```

只要 README 里在任何位置(正文、代码块、HTML 注释皆可)**先**出现一行数字正确的「白名单构成」,
门禁就取它,后面那行**真正的、被改错的**行永远不会被读到。

**同类残留**:同一文件里 **4 处 README 校验全部用 `match` 首匹配**,
不只是新增的这条:

| 行号 | 校验对象 |
| :--- | :--- |
| `:2381` | `跨 WS 集成 N/N` |
| `:2400` | `白名单构成`(**本次新增**) |
| `:2455` | `冻结层不变量 N/N` |
| `:2468` | `未决台账 N 条` |

⇒ 这不是本批引入的新问题,但**本批新增的那条继承了它**。
建议统一改成 `matchAll` + 断言「恰好 1 处匹配」(`matchAll(...).length === 1`),
这样既能保留双向校验,又能把「重复出现」本身变成红灯。

**关于 `\s*` 匹配到别处的担忧**:实测**不成立**。
`待接线\s*(\d+)\s*\/\s*刻意不接\s*(\d+)` 的 `\s*` 只在两个词与数字之间吃空白,
无法跨越到别的位置;真正可利用的是**首匹配**而非 `\s*`。

**反向伪造**:把 `WL_PENDING_RE` 改成永不匹配 ⇒ 分类变成 0/16/34(合计仍 50)
⇒ 门禁**退出 1** 并报「实测 待接线 0」 ⇒ **判据被削弱会被发现**,这一环是好的。

**「等价于关闭防护」需要收窄(我的独立结论)**:

我二分求出「不触发任何违规可稳定维持的最大速度」:

| 声明 `S` | 实测可维持 | 理论 `S × 1.25` | 相对基线 |
| ---: | ---: | :--- | :--- |
| 1.0 | 5.625 格/秒 | 1.250 | 按倍率放大 |
| 1.5 | 8.438 | 1.875 | 按倍率放大 |
| 2.0 | 11.250 | 2.500 | 按倍率放大 |
| 最大合法值 | 有界 | 约 3 倍 | **上限被放大** |

⇒ **可维持速度 = 基线 × 声明值 × 1.25**。准确表述:

- 危害**不是「无限瞬移」也不是「关闭防护」** —— 上限仍**有界**(约基线 3 倍)。
- 准确危害是:**速度上限随声明值等比放大**(从合法余量抬到约 3 倍),

- 单帧瞬移仍被 `TELEPORT` 抓,持续超速仍被 `SPEED` 抓(但检出阈值也被同步放大)。

**物品栏三条(全部复现,且避开了 Lead 警告的 `BURST` 陷阱)**:

| # | 结论 | 我的复验 |
| :--: | :--- | :--- |
| (1) | `FROM_NOTHING` 可绕过 | 空集合 → 拒绝;客户端自带 `{anything}` → **通过**。对照:op 无 `source` 也拒 ⇒ **检查本身有效,只是参数可伪造** ✓ |
| (2) | `OVERFLOW` 可绕过 | `capacity` 报任意大值即通过(已避开其它检查,确认是该分支放行)。
| (3) | `NEGATIVE` 恒不可达 | 复验确认:**空集判断**,该分支在生产不可达 ✓ |

`NEGATIVE` 的代数证明:
`beforeTotal = Σ max(0,-delta) = -net_neg`,故 `after = beforeTotal + net = -net_neg + net`。
全扣减 ⇒ `net = net_neg` ⇒ `after ≡ 0`;全产出 ⇒ `beforeTotal = 0` ⇒ `after = net ≥ 0`。
**⇒ `after ≥ 0` 恒成立,`after < 0` 分支不可达。**

对照(传真值时该分支**正常工作**):

```
beforeTotal=10, delta=-50 → 拒绝 ITEM_NEGATIVE「消耗了不存在的东西:10-50=-40 < 0」
```

⇒ **不是死代码,是参数被换成了循环定义。**

**工具自证**:5 个拒因分支**逐一可单独触发**(`FRACTIONAL`/`FROM_NOTHING`/`BURST`/`NEGATIVE`/`OVERFLOW` 5/5 命中),
且合法输入通过 ⇒ 我的调用链没写坏。

### 5.1 欠账构成门禁:分类仍有一处把接线活说成了等待

新口径 `19 / 22 / 9 / 0`(合计 50)我复算**一致**,判据也能抽出。但 `clientShell` 的 19 条里:

| 归属 | 条数 | 理由 |
| :--- | ---: | :--- |
| `client/src/**` | 16 | 「客户端子系统,本仓无装配入口」 |
| **`server/src/**`** | **3** | 「WS-03 自动贴图,**待客户端接线**」`build/autotile.ts`<br>「WS-08 电路可视视图,**待客户端接线**」`build/wiring_view.ts`<br>「WS-07 客户端预测,**待客户端接线**」`net/prediction.ts` |

这 3 条的理由写的是「**待客户端接线**」—— 是**缺接线动作**(wiring),不是「等客户端入口」(clientShell)。
它们被 `WL_BLOCK_CLIENT_SHELL = /客户端|本仓无装配入口/` 先抓走,因为理由里含「客户端」二字。

⇒ 这与 Lead 自己刚修掉的那个错误**同形**:把接线活归入「等某人/等某事」。
⇒ 准确构成应为 **`clientShell 16 / wiring 25 / mechanism 9 / decision 0`**。

**根因**:判据第一个分支用的是**宽词**「客户端」,而 wiring 分支用的是窄词「待接|等编排层接线|待客户端接线」。
顺序上 clientShell 在前 ⇒ 宽词先命中。**建议**:`WL_BLOCK_CLIENT_SHELL` 收窄为
`/本仓无装配入口|客户端子系统/`(与旧判据一致),或把 wiring 分支提到 clientShell 之前。

**另一处**(较轻):`decision` 的判据不是语义判断「等人拍板」,而是**兜底**
(前三条都没命中,且含意图词+承接词)。它恒 0 是**因为它排在最后**,不是因为「没有待裁决项」。
若将来出现「等 Lead 定 API 形态」,含「等」但不含「接|注入」⇒ 落入 `other`,
而 `other` 在打印里被 `wl.other > 0` 条件显示 —— 会显示,但**不参与 README 双向校验**,
所以不会变红。建议把 `other` 也纳入断言。

### 5.2 ⚠ 信任边界门禁:**恒绿,无法表达「已修」**

这是本轮最重要的发现。门禁自述边界 #1 是「接口级,非字段级」,边界 #2 是
「修复某一条后必须把条目移出 `TRUST_EXEMPT`,否则报白名单失真」。

**四条场景矩阵实测**(改 `room.colyseus.ts` 后跑门禁):

| 场景 | 门禁输出 | exit |
| :--- | :--- | :---: |
| ① 未修 + 白名单保留(现状) | 取自客户端 **3** 处(已登记 3 处) | 0 |
| ② 未修 + 白名单清空 | 报「新增未登记 3 处」 | 1 |
| ③ **真修**(三字段全取服务端值)+ 白名单保留 | 取自客户端 **3** 处(已登记 3 处) | 0 |
| ④ **真修** + 白名单清空(照边界 #2 指引做) | 报「新增未登记 3 处」 | 1 |

**① 与 ③ 的输出逐字完全相同。② 与 ④ 的输出逐字完全相同。**

原因:`ops: msg.ops` 是**合法且必须**的客户端输入(客户端提交要买/要卖什么),
接口级判定只要实参里出现 `msg` 就把**全部 3 个**受管字段标记为「取自客户端」。
而 `ops` 永远来自 `msg` ⇒ `found` 恒为 3 ⇒

- **修好任一字段,`found` 不减** ⇒ 门禁看不出进展;
- **移出白名单则报「未登记」** ⇒ 边界 #2 的「修好就移出」这条路径**走不通**。

⇒ 后果:门禁**永远绿**,且它的绿色**不随修复变化**。
这与本会话反复出现的「假绿」是同一族,但形态更新:
**不是判据失效,而是判据的分辨率低于被测量**。它测的是「该接口引用客户端数据吗」,
而这个问题**答案恒为是** —— 于是它测不出任何东西。

**这不是纯理论**:修复者若照边界 #2 操作,会先看到红(「失真,应移出」),
移出后转绿 —— **门禁绿了,缺陷还在**。报错指引把人推向了错误操作。

**修法已验证可行(字段级,无需数据流分析)**:取该字段在实参里的**取值表达式**再判。
我在内存里对三种代码态实测:

| 场景 | 接口级判定 | 字段级判定 |
| :--- | :---: | :---: |
| ① 未修 | 3/3 | **3/3** ✓ |
| ③ 真修 | 3/3（❌ 看不出差别） | **0/3** ✓ |
| B 别名化(`pkt = msg`) | 0/3（❌ 漏报） | **3/3** ✓（`pkt` 纳入客户端标识符） |

⇒ 字段级在三个场景全对,且顺带修掉一个漏报(别名化)。
残余:若实参整体透传(`applyInventory(sid, pkt)` 而字段名不出现),字段级无法判定 ⇒
**回退到接口级**(保守多报)。两模式结合即可。

### 5.3 `SERVER_OWNED_INPUTS` 盲区里正好有 2 个已确认缺陷

受管表只有 `applyInventory`。而扫描正则覆盖 `applyMove|applyAttack` —— 它们被扫到,
但 `SERVER_OWNED_INPUTS[method]` 为 `undefined` ⇒ `continue` 跳过。

⇒ 我上一批已实测这两个是**同族缺陷**:
`applyAttack` 与 `applyMove` 的客户端声明都会直接放大阈值。
⇒ **门禁对两个已确认的缺陷点结构性看不见。**
注释已自述「受管字段表是人工维护的,这是残余风险」——但该风险**当前已实现**,
应显式登记「盲区内有 2 个已知缺陷」,否则读者会以为「信任边界 3 处已登记」就是全部。

### 5.4 影子行:只修了 4 处里的 2 处

上一轮我指出「同文件 4 处 README 校验都是 `match` 首匹配」。本轮实测:

| 校验 | 行号 | 写法 | 影子行 |
| :--- | :--- | :--- | :---: |
| 跨 WS 集成 | `:2536` | `matchAll` + 唯一性 | ✓ 挡住 |
| 欠账构成 | `:2562` | `matchAll` + 唯一性 | ✓ 挡住 |
| **冻结层不变量** | **`:2626`** | **`match`(首匹配)** | **✗ 静默放行** |
| **未决台账** | **`:2639`** | **`match`(首匹配)** | **✗ 静默放行** |

实测(影子行插在前、真行改错):两条都**退出 0**;对照组(仅真行错)都退出 1。
⇒ 「4 处」只修了 2 处。

关于 Lead 自述踩过的坑(**影子行必须带前缀才算影子行**)——我复验:**成立且必要**。
测试「不带前缀的假影子行」时,门禁报的是「**只校验首处会让其余成为影子行**」之外的另一条

因此「插入不带前缀的行后仍被绕过」这个观察,指向的是**探针**,不是门禁 —— Lead 的自我更正正确。

### 5.5 本轮我自己的工具错误(新增 3 个)

| # | 错误 | 现象 | 若不修的后果 |
| :--: | :--- | :--- | :--- |

| E9 | 用 `(Get-Content f).Count` 判行数 | 报 **2618**,而文件实为 **2869**;我一度怀疑自己损坏了 `verify.ts` | 会误报「文件被破坏」,并可能触发一次不必要的还原 |

**E7 值得记**:我拿「半修应该变红」当阳性对照,但门禁**自述**是接口级、答不了半修状态。
⇒ **阳性对照必须按被测对象的自述口径设计**,不能按我期望的口径设计。
否则会把「它如实声明的边界」误判为「它坏了」。

**E9 的根因(重要,与环境有关)**:本环境的 `Get-Content` 以 GBK 解码 UTF-8 源文件,
中文乱码后**相邻行被合并**(实测 `node[1]` 与 `node[2]` 在 PS 口径下并成一行),
于是 `.Count` 偏小。判据:

| 口径 | 行数 |
| :--- | ---: |
| `node -e "readFileSync(...).split('\n').length"` | **2869** ✓ |
| 模拟 .NET `ReadLine`(按 `\r\n`/`\r`/`\n` 逐个终止) | **2868** ✓ |
| `(Get-Content f).Count` | 2618 ✗ |

**核实文件未损坏的四条证据**:① node 口径 2869 与 `read` 工具早前读数一致;
② 关键符号行号全部吻合(`whitelistBreakdown:653`、`TRUST_EXempt:1179`、`checkClientTrust:1198`);
③ `verify.ts` 实际运行**全部通过**(5810ms, exit=0);④ `matchAll` 出现 10 次,与修改前一致。
⇒ **结论:文件完好,是工具口径错。** 本环境数行数**必须用 node**,不要用 `Get-Content .Count`。

> 我的**警觉是对的**(行数突变必须查),但**归因错了**(先怀疑自己损坏文件)。
> 这正是本会话反复出现的形态:**工具先于被测对象出错**;区别只在于这次错在 PowerShell 的编码成见。

### 5.6 本轮结论

| 项 | 结论 |
| :--- | :--- |
| 欠账构成 19/22/9/0 | 合计与判据**可复现**;但 3 条 `server/src/**` 的「待客户端接线」被错分为 `clientShell` ⇒ 应为 **16 / 25 / 9 / 0** |

**优先级建议**:
1. **信任边界改字段级**(高)—— 现状恒绿,比不装更危险:它让「已检查」看起来成立。
2. **`冻结层` / `未决台账` 补 `matchAll` + 唯一性**(中)—— 与已修的两处保持一致,成本极低。
3. **`clientShell` 判据收窄**(中)—— 否则 3 条接线活继续被说成「等入口」。
4. **受管表补 `applyMove`/`applyAttack`(或显式登记盲区)**(中)—— 建议至少做后者,成本最低。
