## 一、还原可靠性自证(对象:`verify.ts` 本身)

Lead 提醒「注入前先证明还原可靠」。本轮要反复改 `verify.ts`,故自证对象换成它:

| # | 场景 | 结果 |
| ---: | :--- | :--- |
| ① | 正常路径:`finally` 还原 | ✓ 哈希一致 |
| ② | 注入中途抛错:`finally` 仍还原 | ✓ |
| ③ | **检出反证**:故意不还原 ⇒ 必须报不一致 | ✓ 报了一致性差异 |
| ④ | 二次正常:无累积污染 | ✓ |

### 1.1 但本轮**真实发生了一次事故**,并暴露自证的第 5 个盲区

写交叉分析脚本时**漏导入 `writeFileSync`**,脚本在第 39 行 `finally` 崩溃:

```
ReferenceError: writeFileSync is not defined
  } finally { writeFileSync('scripts/verify.ts', orig); }
```

**`verify.ts` 哈希仍是原值** —— 但查清原因后,这不是「设计得救」,而是**巧合得救**:

> 注入**和**还原共用同一个 `writeFileSync`。它未定义 ⇒ 注入没执行、还原也没执行
> ⇒ 文件**压根没被动过**。
>
> 若注入走 A 机制、还原走 B 机制,而 A 成功 B 失败 ⇒ **就会停在注入态**。
> 这正是本会话已有三次事故的成因。

**因此补第 5 项自证**:

| # | 场景 | 做法 |
| ---: | :--- | :--- |
| **⑤** | **还原路径自身可用性** | 注入**之前**先断言 `writeFileSync` 是函数、目标可读、真实回写一次且哈希不变;**不可用则拒绝注入**(`process.exit(5)`) |

集成后实测:`✓ 通过,允许注入`。本轮此后所有注入都经此门。

> **教训**:前 4 项自证的是「还原逻辑对不对」,第 5 项自证的是「还原**代码能不能跑**」。
> 前者靠推理,后者只能靠**事前探测** —— 因为崩溃发生在 `finally` 里时,
> 你连报错的机会都没有(本次那个脚本连自己的错误处理都没跑完)。

## 四、⚠️ 本轮找到的**真实缺陷**:可断言数字**只在绿灯时打印**

Lead 的原始要求是「**必须打印可断言数字**」。复核发现**两个门禁都只在通过路径打印**:

| 门禁 | 数字行 | 打印条件 |
| :--- | :--- | :--- |
| R6 | `可达 N / 不可达 M(共 K,白名单 B 条)` | 仅在 `if (missingEntries.length === 0 && stale.length === 0)` 内 |
| S11 | `命中 N 条(白名单 M 条)` | 仅在 `if (stale.length === 0)` 内 |

**失败时数字消失。** 实测原始输出:

```
✗ 同义反复白名单失真(8 处,应修正):WS-01::BARE_GROUND_MU(已不再命中); ...
i 同义反复候选:命中 43 条(白名单 50 条)(白名单失真 7 处,见下方)   ← 修复后才有
```

**为什么这是真缺陷**:失败时你恰恰需要**同时**知道两件事 ——
① 出了什么问题;② **总数有没有跟着变**。
② 才是区分「修复落地」与「有人动了别处」的唯一依据。原实现中 ② 在失败路径不可见。

**已修复**:两个门禁的数字行改为**无条件打印**(失败路径以 `i` 前缀输出,与 `✓`/`✗` 区分)。
本轮白名单收缩正是靠它才看清「命中数一路下降」。

## 五、重点关注:两个门禁会不会**互相掩盖**?

Lead 特别要求查这个。分三层:

### 5.1 执行顺序 —— 无掩盖

`main` 里的调用是**平铺、无条件**的,不是 `&&` 串联:

```
1. checkStrippable()
2. checkReachability()
3. checkTautology()
```

实证:让 R6 故意 fail(塞不存在的入口),**S11 仍然照常执行并输出**。
`fail()` 只累加计数、不 `process.exit`,所以前者失败不会中断后者。

> **我在这里犯过一次错**:第一次跑交叉分析时,我用自己的正则去找 `同义反复候选:命中`
> 判断「S11 是否被执行」,得到「被跳过(掩盖!)」——**结论是错的**。
> 抓原始输出后发现 S11 一直在跑,只是**失败路径不打印那行数字**(即 §四 的缺陷)。
> **我的检测方法与被测对象犯了同一个错**:用「绿灯行是否存在」推断「是否执行」。
> 这是本会话第 6 次自我拦截,也是第一次**「错误结论恰好指向一个真缺陷,但理由完全不对」** ——
> 若我据此写「门禁互相掩盖」,就会报一个假缺陷并漏掉真缺陷。

### 5.2 交叉统计 —— 存在**信息盲区**(非掩盖)

两份白名单互不关联:R6 只管「模块在不在生产闭包」,S11 只管「断言右侧是不是被测常量」。
一个模块可以同时「不可达」+「含同义反复」,**两边都报「已登记」,没有任何地方提醒**。

实测 50 条同义反复候选按模块可达性分布:

| 分类 | 数量 | 含义 |
| :--- | ---: | :--- |
| 落在**可达**模块(生产会跑) | **18** | 真危险:同义反复直接掩盖生产行为偏差 |
| 落在**不可达**模块(生产不跑) | **32** | 次要:该模块本就未被接线,风险等级不同 |

可达侧的 18 条(节选):`WS-04` 的 `behaviors.ts` 一族(9 条)、
`WS-01 world/chunk.ts` 2 条、`WS-07 net/delta.ts` `PROTOCOL_VERSION`、
`WS-FND-02 events/bus.ts` 2 条。

**结论:这不是「互相掩盖」(没有哪一边被消音),而是「缺少交叉标注」。**
S11 的白名单理由字段里看不到「该模块是否可达」,而这对排序修复优先级**直接有用**。
已列为建议 S20 —— **不修改门禁**(改动会引入新风险),只作为人工审计时的排序依据。

### 5.3 诚实区分:哪些没做出来

| 想注入 | 为何没做 | 定性 |
| :--- | :--- | :--- |
| 「既不可达又含同义反复 ⇒ 被双白名单静默接受」 | **做不出来** —— 这不是可注入的缺陷,两个门禁各自都按设计工作;这是**设计层面的信息缺口** | 真实但非缺陷(§5.2) |

**没有发现「装饰性门禁」** —— 两个门禁的每一项注入都产生了可观测差异。
