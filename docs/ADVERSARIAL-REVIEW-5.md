### 4.1 一个重要的设计决定:它**只报候选,不做判定**

我先尝试做一个**判定器**,静态判据 P:

> 同套件内另有一条断言把该常量与**数值字面量**比对 ⇒ 该常量有独立锚点 ⇒ 不是同义反复

用**已知答案**交叉验证(21 个 S7 实证的真同义反复 + 9 个 S7 实证「有牙齿」的常量):

| 校验 | 结果 |
| :--- | :--- |
| 真同义反复被判「无锚点」 | 16 / 21 |
| 真同义反复被**误判**「有锚点」 | **5 / 21** |
| 有牙齿被判「有锚点」 | 5 / 9 |
| 有牙齿被**误判**「无锚点」 | **4 / 9** |

**P 不等价 ⇒ 不能当判定器。** 两侧都有 20~45% 的错误率,
用它报缺陷会既漏报又误报。真正的判定只能靠注入法(人工流程)。

> 这是本批第二次「先验证判据、再决定是否采用」。
> 若我直接把 P 写进门禁并 fail,它会立刻产生 5 条假缺陷 + 漏掉 4 条真缺陷 ——
> **一个比没有门禁更糟的门禁。**

### 4.2 门禁的实际形态

```
[同义反复候选]
✓ 同义反复候选:命中 50 条(白名单 50 条)
```

**四层保障**(与 R6 同构):

| 层 | 做法 | 实测 |
| :--- | :--- | :--- |
| 可见 | 默认**告警**非 fail | 新增候选 → 报出 `套件 常量名` |
| **数字** | 命中数与白名单数**硬打印** | 50 / 50,任一变化可察觉 |
| 收紧 | `--strict-taut` 升级为失败 | **退出码 1**,报 `新增未登记的同义反复候选 N 个` |
| 自检 | 白名单**四种失真**全检 | 见 §4.3 |

**白名单粒度 = `套件::常量名`,50 条**。粒度选套件而非行号,是因为
同一常量在一个套件里可能出现在多行(`BREAK_CRIT_BONUS` 有 4 行);
选行号会让修复时白名单大面积失真。

**必须带套件名**:实测发现 **6 组跨模块重名常量** ——
`ICON_SIZE`(`pixel_icon.ts` / `entity_sprites.ts`)、
`DYE_PALETTE_SIZE`(`dye_overlay.ts` / `scoring.ts`)、
`S_LOGIC_FLOOR`、`S_LOGIC_CEIL`、`BOUNCE_VZ`、`BOUNCE_VZ_ANALYTIC`。
只按常量名登记会**张冠李戴**。

### 4.3 故障注入:4 项全部生效

| # | 注入 | 观察 |
| ---: | :--- | :--- |
| A | 新建 `tests/_S11A.test.ts`,引入未登记候选 | 命中 **50 → 51**;告警报出 `_S11A::PROTOCOL_VERSION` |
| A' | 同上 + `--strict-taut` | **退出码 1**,`✗ 新增未登记的同义反复候选 1 个` |
| B | 白名单条目改成不存在的常量名 | `✗ 同义反复白名单失真:...(已不再命中,应移出白名单)` |
| C | 白名单理由写成 `'x'` | `✗ ...(未写明理由)` |
| D | 把 `WS-10:319` 的常量换成字面量(模拟修复) | `✗ ...WS-10::REFLECT_RADIUS(已不再命中,应移出白名单)` |

**注入 D 是最有价值的一项**:它证明白名单**会随修复单调收缩**。
修好一处而不同步移出白名单,门禁立刻报错 —— 这样白名单不会烂在原地,
也不会被当成永久豁免。**这是它与「加了白名单就永不失败」的分界线。**

`verify.ts` 每次注入后哈希比对,收尾一致(`4fd955e7695ec908`);探针文件已删除。

### 4.4 已知边界

- 只跟踪静态 `import`,不跟踪动态 `import()`(与 R6 同一边界)
- 只识别 `eq/near` 的**第二实参**;若常量写在第一实参(`eq(CONST, x)`)会漏
- **不判定**,所以稳态下永远是「50 命中 50 白名单」全绿;
  它的价值在**新增候选**和**白名单收缩**两处

## 5.1 更正:WS-FND-03 **不是**空套件(我的判断错了)

我最初用 `Select-String '^test\('` 数出 **0 条**,据此在未决里写下「空套件(0 条断言)」,
并推测「该文件为何存在却没有断言?」。

**实际运行后推翻**:

```
$ node tests/WS-FND-03.test.ts
[WS-FND-03] 106/106 通过
```

它**有 106 条断言**,只是**没有用共享的 `test()` 包装** —— 该文件自带一套
极简 harness(`const ok` / `const eq` / `const okHas`,自计 `pass`/`fail`,
末尾 `if (fail > 0) process.exitCode = 1`)。

**我的错误在于**:把「符合共享 `test()` 形态的行数」当成了「断言总数」。
这两件事在 16 个套件里恰好一致,**唯独这个套件不一致**,于是我的计数法静默失效。

> 这是本会话**第 4 次**靠实证拦住自己的先验(前三次:`rowAligned` 恒真、
> WS-08 全盘假绿、`AREA_TOO_SMALL` 不可达)。
> 但这次与前面不同:前三次我是在**报缺陷之前**自我拦截,
> 这次我**已经写进了未决清单**才去核实。
>
> 教训更具体:**「用 grep 数出来的 0」和「实际没有」是两回事。**
> 凡是要断言「某处为空/为 0」,必须先证明计数方法对该处有效 ——
> 我这次缺的正是这一步。

**顺带发现两条值得记的事实**:
1. 全仓 17 个套件里,有 **1 个**使用自带 harness。若将来有工具按 `^test\(` 统计覆盖率,
   会把它算成 0 —— **这正是我在未决里想表达的风险,只是原因猜错了。**
2. 该套件 106 条断言覆盖 `handshake.ts` 内容版本协商,是**活跃且完整**的,
   建议后续把它作为「自带 harness 也能被 verify 正确统计」的回归样例。
