### 2.2 ★★ 唯一「不红」的那一条:S4a —— 这是本卡最重要的实测

**站点**:`tests/WS-09.test.ts`(HEAD 版 `L3813`,工作区版 `L3831`)
```ts

  const L = layoutInventoryPanel(VW, VH);
  eq(L.cols * L.rows, L.cols * L.rows, '网格格数 = 列×行');   // ← 目标断言
  ok(CELL_INSET * 2 < L.cell, `内缩 ${CELL_INSET}×2 < 格宽 ${L.cell}`);
  const r0 = slotRect(L, 0);
  const r1 = slotRect(L, 1);
  eq(r1.x - r0.x, L.cell, '相邻格水平间距 = 格宽');
  ...

```

**注入**:`layoutInventoryPanel` 里 `const gridW = cols * cell;` → `+ 7`
```
基线    [WS-09] 104/104 通过
注入后  [WS-09] 104/104 通过      ← ★ 全绿,没有任何一条发现 gridW 被改坏
```

**★ 诊断(两层,缺一不可)**:
```
第 1 层:这条断言**结构上不可能失败**
   两侧是**完全相同的表达式** `L.cols * L.rows`,同一个对象、同一次求值。
   不是「期望值写错」,是「**它根本不是断言**」—— 恒等式的两边是同一个东西。
   ⇒ 工具的正确判定:`乙-like(两侧同一表达式)` ✓

第 2 层:这条 test **另有**一条断言在撑牙(S4b 证明)
   我把 CELL_INSET 改成 99999 ⇒ 103/104,**红的正是同一条 test**
   红的**不是**目标 eq,而是 `ok(CELL_INSET * 2 < L.cell, ...)`
   ⇒ ★ 「这条 test 会红」**不能**推出「这条 test 里每条断言都有牙」。
     test 名是**块级**标签,不是**断言级**标签。
```

**★ 而且第三个层面更隐蔽 —— 标题声称的不变量根本没被守**:
```
test 标题写「格子数 × 格宽 = 网格宽」,即期望守   cols * cell === gridW
但它实际比的是                       cols * rows === cols * rows
⇒ 两个都不对:比的是**格数**(cols×rows),标题说的是**宽**(cols×cell)。
  真正的「网格宽」在 `gridW` 局部变量里,而它**没有出现在返回对象中**;
  能间接观测它的只有 `title.w` / `tabStrip.w` / `pager.w`(三者都赋 `gridW`)。
  ⇒ 而**没有一条断言**看这三个字段。**⇒ 这就是它改了都不红的原因。**
```

## 3. ★★ 失效边界(本卡的核心价值,不是附录)

### 3.1 工具的**已知**边界(文件头自述,6 条)

```
B1 只做**句法级**候选分析 —— 报的是「注入能不能够到」,不是「有没有牙」
B2 判不了「**守错对象**」(陷阱 60)—— 它只看表达式的**文本形状**,
   不知道这个断言**本该**守什么
B3 判不了「**性质类断言**」(陷阱 57)—— 如「单调递增」「无副作用」
B4 看不见**被调函数内部** —— 只扫表达式文本;
   `Math.random` 藏在 `EventBus.emit` 里时它看不到 ⇒ 这类 **乙-B 列恒 0**
B5 「**无生产候选**」≠「没牙」 —— 守测试夹具不变量的断言就该如此
B6 同名方法**全取** —— 方法索引是同名即命中,不做类型/重载解析
```

### 3.2 ★ 本卡**新实测出**的边界(工具自述里没有)

#### 新增边界 N1:**「无生产候选」有两种成因,工具用同一句话报,而处置相反**

```
成因 A:断言里的标识符**确实**回不到任何生产定义(如 `eq(g.maxHp, 100)` 里的 g 是测试局部)
       ⇒ 正确处置:**这条断言守的是测试夹具不变量,可能完全正确,不该动**
成因 B:断言两侧是**同一表达式**(自反),任何生产改动都动不了它
       ⇒ 正确处置:**这条断言是坏的,必须重写成能观测生产输出的形式**

★ 工具的报出文本对两者**完全相同**:
    「★ 无生产候选 —— 注入生产**永远不会**让它红」
  ⇒ 只读这一句的读者**无法区分**「我守的是夹具(没问题)」与「我恒真(有问题)」。

★ 缓解:工具在**分类标签**里给了区分(成因 B 会打 `乙-like(两侧同一表达式)`)。
  实测 L3831 的输出:
    ★ L3831 [eq] 乙-like(两侧同一表达式)
      实际: L.cols * L.rows
      期望: L.cols * L.rows
      ★ 无生产候选 —— 注入生产**永远不会**让它红
      仅测试内: L(本文件声明)
  ⇒ **信息在里面,但不在标题里。** 扫清单的人会漏。
  ⇒ ★ 建议(未实现):把成因 B 的报出文本改成
    「★ 自反比较 —— 两侧同一表达式,**结构上不可能失败**,必须重写」,
    与成因 A 的「守夹具,属正常」分开。
```

#### 新增边界 N2:**「文件红了」不等于「目标断言红了」**

```
证据 = S4a:S4b 让**同一条 test** 变红,而 S4a 让**同一条 test** 全绿
⇒ 同一 test 块内,断言之间**牙齿不齐**。
⇒ ★ 工具按**断言**粒度报(正确),但人读测试报告时按 **test 名**读(会错)。
⇒ 任何「注入 ⇒ 看它红不红」的自动化流程,必须比到**断言级**,
   否则「兄弟断言红了」会被误记为「这条断言有牙」—— 这正是 S4a 骗过朴素流程的方式。
```

#### 新增边界 N3:**锚点匹配是行尾敏感的**(我踩了两次)

```
实测:`server/src/events/bus.ts` 是 **CRLF**;我用 `\n` 拼的锚点
      ⇒ `includes(from)` = false ⇒ 注入被**静默跳过**(报「锚点未找到」)。
      ⇒ 第一次我还误以为「S3 没红」,其实是**没注入成功**。
★ 这条对**任何**做「改源码再跑」的脚本都成立:
   必须先测目标文件的**自身行尾**(本卡:`readFileSync(p).includes('\r\n')`),
   不能假定 `\n`。仓库里行尾是**逐文件不同**的(WS-10 是 LF,bus.ts 是 CRLF)。
```

#### 新增边界 N4:**只认字面量 `test(` ⇒ 有套件会被静默报成「0 条断言」**

```
实测:`extractTests()` 的入口是 `const re = /\btest\s*\(/g;`(工具 L242)
⇒ 两个套件被报成「断言 0 条」,而它们的**真断言调用数**是 97 与 21:
     WS-FND-03  自建 pass/fail 计数器(不 import shared harness)⇒ 无 `test(` 块
     WS-FND-13  import 了 harness,但用 `async function atest(...)`(L67)
★ 后果与「方向反了」那次**完全同型**:静默的 0 会被读成「这里没有断言」。
  详见 §1.2(含逐文件证据表与建议)。
★ 自检办法(我也正是这样发现的):**把「真断言调用数」与「解析出的块数」对拍**。
  两者差得离谱(97 vs 0)就说明解析器不适用,而不是套件没有断言。
```

```
维度甲 —— 「有牙吗」:注入生产 ⇒ 这条断言会红吗?
   验证手段:**注入自检**(改生产源、重跑、看是否红)
维度乙 —— 「红了说明什么」:期望值是不是**独立**于被测实现的?
   验证手段:**同义反复检测**(`--strict-taut`)

★ 两者**互相推不出**:
   甲绿 ⇒ 会红,但**不**推出红了代表实现错了(可能两侧同源一起动)
   乙好 ⇒ 期望值独立,但**不**推出这条断言会被跑到(可能它永远为真)
```

### 4.2 四象限(每一格都有一手证据)

|  | **乙好**(期望值独立) | **乙坏**(期望值与被测同源/自反) |
| :--- | :--- | :--- |
| **甲绿**(会红) | ① 理想。S1/S2/S5/S6 实测都红 | ② ★ **最危险**。见 4.3 我的那颗 |
| **甲坏**(不会红) | ③ 罕见:期望值独立但够不到(理论上) | ④ S4a:`eq(L.cols*L.rows, L.cols*L.rows)` |

```
★ 危险度排序:② > ④ > ③ > ①
  ②「甲绿+乙坏」最危险:**它看起来完全正常** —— 注入会红、CI 会绿、
    一切检查都过,但**它红的含义是错的**(实现一变,期望值跟着变,永不报警;
    或反过来,实现是对的它也红)。**它是伪装成健康的病。**
  ④「甲坏+乙坏」反而**更容易被发现** —— 因为它连红都不会红。
```

### 4.3 ②象限的**我的一手证据**(不是引用,是我自己犯的)

```ts
// 我写的(task-64),被门禁抓出来的:
eq(gv.iframeSec, MANUAL_REVIVE_INVULN)
```
```
为什么是 ②:
  MANUAL_REVIVE_INVULN(server/src/combat/revive.ts:34 = 0.5)正是
  revive.ts:222 **写进** DownedState.invulnSec 的那个常量。
  ⇒ 同一个常量既写状态、又当期望值 ⇒ **两侧永远一起动** ⇒ 断言**永不可能失败**。
★ 关键:这条断言**通过了注入自检** —— 我若去注入 revive.ts,它会红(因为两边一起动)。
  ⇒ **注入自检过关,推不出期望值来源正确。**
★ 抓住它的是 `scripts/verify.ts --strict-taut`:
    ✗ 新增未登记的同义反复候选 1 个(--strict-taut):WS-10::MANUAL_REVIVE_INVULN
★ 修复:改用字面量 `0.5` + 注释引设计基线,与文件既有风格一致
  (`eq(s.lastRevive!.invulnSec, 0.5, ...)`),并删掉不再使用的 import。
```

### 4.4 结论(可直接引用)

> **「注入自检过关」与「期望值来源正确」是两个正交的性质。**
> 前者管**可观测性**(改了生产,这条断言会不会动),
> 后者管**语义有效性**(它动的含义对不对)。
> 单独任何一项**都不充分**;而 `assertion-teeth-report`(维度甲)与
> `--strict-taut`(维度乙)恰好各覆盖一个,**必须同时跑**。
>
> ★ 并且:**这两个检查的盲区也不重叠** ——
> 维度甲看不见「同源期望值」(它只问会不会红);
> 维度乙看不见「自反比较」(自反不是同义反复,是恒等式,`--strict-taut` 的模式
> 抓的是「两侧引用同一个被登记常量」,而 `cols*rows` 两侧是**同一个表达式**,
> 没有常量可登记)。
> ⇒ S4a 这类缺陷,**恰好掉在两个工具之间的缝里**。这是本卡实测出的一条新缝。
