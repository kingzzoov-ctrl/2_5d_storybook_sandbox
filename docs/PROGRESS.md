## 〇-3、门禁的两个新缺陷(本轮实测发现,**均已修复**)

> 这两条与 `docs/GATE-AUDIT-13.md` 的 D1–D5 **同类** —— 都是「门禁说的和门禁做的不一致」。
> 但严重度更高:它们让**整套客户端与整套战斗公式在门禁里隐形**。
> **状态:2026-11-12 由 task-32 修复,证据见本节各条「修复后」。**

### 缺陷一:可达性门禁漏掉了整个客户端

`scripts/verify.ts` 的 `PROD_ENTRIES` **只有两项**(都是 server 的):
```
'server/src/sim/demo.ts'
'server/src/net/room.colyseus.ts'
```
**没有客户端入口。** 而本会话建了 `client/index.html` + `client/src/main.ts`,
它真的能跑(截图验证:60 FPS / 等轴测地形 / 图集立牌),但门禁不知道。

实测后果 —— 门禁把这 4 个**正在被浏览器加载**的模块报成「新增未登记的不可达模块」:
```
· client/src/main.ts
· client/src/stage/chunk_geometry.ts
· client/src/stage/demo_world.ts
· client/src/three/boot.ts
```

**根因**:入口表是手写的,加客户端时没人想到要同步它。
这与 D2(契约表可被清空仍全绿)**同类** —— 都是「关键清单靠人维护,而没有任何东西检查它是否跟上了现实」。

**修复后**:`PROD_ENTRIES` 补上 `client/src/main.ts`;另加断言
「`client/index.html` 必须引用 `./src/main.ts`」,防两者再次脱节。
数字变化:**可达 31 → 43 / 不可达 47 → 35 / 入口 2 → 3 个**。

### 缺陷二:白名单理由已成事实错误

16 条 `client/**` 白名单条目的理由都是「**客户端子系统,本仓无装配入口**」。
但实测:
```
client/index.html      存在? true
client/src/main.ts     存在? true
```
理由里的「无 index.html / main.ts」**是假的**。

**这是本项目最忌讳的形态:白名单因事实变化而静默放宽。**
现有自检抓「文件不存在」「已可达」,**抓不到「理由本身过时」** ——
一条理由可以在代码早已变化后继续为白名单提供豁免,而门禁全程绿色。

**修复后**:新增 `detectStaleReason()` 专门抓这一类(否定式存在断言 + 路径引用必须存在),
并把这条推广成通用陷阱写进 §七.16。同时给剩余 8 条写了**各自的、当前的**理由
(不再用笼统的目录级说法)。

### 把 `main.ts` 当入口后的闭包实测

递归相对 import 的闭包 **15 个文件**(12 个 client + 3 个 shared/types)。
⇒ 客户端白名单 16 条里 **8 条会变可达**(应移出),**8 条仍不可达**:

### 缺陷三:`WS-10` 的八步伤害公式在生产从未执行

`server/src/combat/damage.ts`(505 行)实现手册要求的八步公式,导出
`computeDamage` / `applyDamage` / `reflectFrom` / `planSkillHits` / `makeDot` / `healTarget`。

**全仓 `computeDamage` 调用点只有 3 处:门禁自检 2 处 + 测试 1 处。生产调用点 = 0。**

真实伤害走 `server/src/combat/vitals.ts:148`:
```ts
export function mobHitDamage(level: number, mul = 1.0): number {
  const base = MOB_HIT_BASE + MOB_HIT_PER_LEVEL * (lv - 1);
  return Math.max(1, Math.round(base * mul));
}
```
即**纯等级线性缩放** —— 没有护甲、没有水晶护甲 ×0.20、没有破甲阈值、
没有 3 格反射、没有浮动文字、没有 DOT、没有技能多段命中。

**旁证:白名单自己承认了** ——
```
scripts/verify.ts:625
['server/src/combat/damage.ts', 'WS-10 八步伤害公式 —— 生产走 vitals.ts 简化路径,待接线'],
```

**比 G-1 严重的地方**:G-1 是「测试测不住一个真在跑的实现」;
这一条是「**测试测的是一个根本没在跑的实现**」。505 行 + 44 条断言全绿,玩家一点感觉都没有。

> **给未来的教训**:「有实现、有测试、全绿」这三件事**加起来仍不足以证明功能存在**。
> 必须问第四个问题:**生产路径真的走到它了吗?** 这已经在本项目里出现 4 次
> (流体相变产物 / 电路件 / 炼金 6 模块 / 八步伤害公式)。

2. **方位角必须是 -45°**:照抄社区惯例按 +45° 摆相机,横向差 **70 个格当量**,同样不报错。
3. **`Math.max(0, {})` = NaN**:`dist > NaN` 恒 false ⇒ 瞬移/均速/攻速**三道检查同时静默失效**,单帧跳 200 格直接放行。这是比「上限多大」严重得多的缺陷。
4. **「等编排层接线」这个分类会掩盖真缺口**:炼金 6 模块的差异表原本读作
   「6 个都在等上游机制」。实际测量后是**6 个都在等同一次接线**,
   而 4 个模块的剩余缺口分别属于网关 / WS-07 / WS-09 / WS-10 ——
   是**别人的债被算在了炼金头上**。分类口径会直接误导排序。
5. **CR-14 U2 必须拆三条,不能合成一条**:U2-a(上限随声明放大,是**取舍不是修复**)、
   U2-b(非数字声明产 NaN,三道检查静默失效,**真缺陷、已修**)、
   U2-c(引用物品 ID 标错 `719/731`→`729`)。
   三者严重度与处置完全不同;混成一条会让读者以为「U2 还是老样子」
   或反过来以为「U2 已经修好了」—— 两种都是错的。
   **U2-a 实测数字**:窗口均速上限 = 4.5 × 2.55 × 1.25 = **14.344 格/秒
   = 基线的 3.188 倍**;攻速声明 `1.0` 即拿满 2×;绕过装备前置**仍然成立**。

## 七、已知工具陷阱(避免重复踩)

1. **`verify.ts` 的 `fail()` 写 stderr** —— 只抓 stdout 会误判「没红」。

3. **`Get-Content` 把 UTF-8 当 GBK** —— 读文件用 node。

5. **`eq()` 抛异常会中断同测试后续断言**(S30)。
6. **`write` 工具可能写到父目录** —— 显式传绝对路径。
7. **`npm` 须用全路径** `C:\Program Files\nodejs\npm.cmd`。

9. **`raw.githubusercontent.com` 有 5 分钟 CDN 缓存** —— 判断「是否已删除」要用 API 或 git 协议。
10. **`git push --force` 不清服务端对象** —— 旧提交仍可按 SHA 读出。
11. **`file://` 打开构建产物会被 CORS 拦**(ES 模块 origin=null) —— 截图必须走 HTTP。本地起服务:`node _cs_serve.ts dist/client 5199`。
12. **`manualChunks` 只接受函数形式** —— 对象形式报 `manualChunks is not a function`。
13. **注释里的 import 会被门禁误判** —— 已修(`stripComments`);写示例时不必再迁就门禁(**这是重点**:不要让工具约束扭曲文档表达)。
14. **行号会因并发编辑漂移** —— 多 agent 同时改文件时,`file:line` 引用要重新定位。
15. **故障注入必须语法合法** —— 写坏文件也能让它红,但那是解析失败,**不构成证明**。
16. **白名单理由会因事实变化而过时,而自检只查「文件存在」与「可达性」**(task-32,已修)
    —— **本条是元级陷阱,比它列举的那一个具体案例更重要**:任何「条目 + 理由」式白名单都会中招。
    实测案例:`client/**` 16 条的理由是「客户端子系统,**本仓无装配入口**」。写上时是**事实**
    (`client/` 确实没有 `index.html` / `main.ts`),后来补上客户端入口后它**变成假的**,
    而门禁**全绿**——因为两处自检都只看条目与文件系统的关系,不看**理由说了什么**。
    当时的后果更糟:因为 `PROD_ENTRIES` 也漏了客户端入口,那 16 条不但理由过时,
    还把 8 个**正在被浏览器加载**的模块说成「未登记」。

    **推广**:凡是有「登记 + 原因说明」的地方(豁免表、白名单、`TRUST_EXEMPT`、
    `TAUT_SUSPECT_EXEMPT`),都要问一句:**这个理由是「事实陈述」还是「设计决策」?**
    - **事实陈述**(「本仓无 X」「X 未安装」「尚无 Y 文件」)⇒ **会过期,必须机器校验**,
      或至少写成可判定的句式(带路径、带否定词),否则它只是装饰。
    - **设计决策**(「刻意不接,等 US7 拍板」)⇒ 不会自动过期,但要写明**谁在等什么**。

    **修法**(已落地):`verify.ts` 的 `detectStaleReason()` 做两道窄网 ——
    ① 否定式存在断言(「无 `index.html`」而它存在 ⇒ 报);② 理由里的路径引用必须存在。
    另加 `client/index.html` 与 `PROD_ENTRIES` 的一致性断言,防入口再次脱节。
    **局限要记住**:它不是自然语言理解,抓不到「字面仍成立但语义已变」的情形
    (如「随 `damage.ts` 一起接」在 `damage.ts` **真被接线后**依然字面成立)。
    补网的方向是**把理由写成可判定的形式**,不是把正则写得更宽 ——
    宽正则会把正确的理由误判成过时,让人开始无视这条告警,那比没有更糟。

    另注:写这条陷阱时也踩了一次同类的坑 —— **统计口径依赖正则写法**。
    `whitelistBreakdown` 的「等裁决 0」曾被读成「没有待裁决事项」,实测却发现
    35 条里 **35 条**都符合「等裁决」的两个正则,只是全部被更具体的桶先抓走;
    把 `WL_BLOCK_MECHANISM` 里的「尚未注入」去掉,同一张表就会算出
    `mechanism 1 / decision 2`。⇒ **0 可以是分类顺序的产物,而不是测量结果。**
    门禁现在会把这个影子数一并打印出来。

17. **单点注入只能证明「该点被抓」,证明不了「整条区间被抓」**(本轮实测,`net-persist` 发现)
    —— **本条的元级意义:它抓的是「验收标准本身」的漏洞,不是代码的。**

    验收标准写「把常量改成荒谬值,断言必须变红」。按字面执行会挑一两个值试,
    而**单边盲区**恰恰能躲过这种试法。实测案例:

    ```ts
    // taming.ts:217
    if (now - pet.lastProduceAt < RANCH_PRODUCE_SEC) continue;
    // 原测试:lastProduceAt = 0,调 tickRanch(pets, 600)
    ```

    ⇒ `600 < RANCH` 对**任何 RANCH ≤ 600** 都为假。把 `RANCH_PRODUCE_SEC` 从 600
    改成 **2 / 10 / 100 / 300 / 500 / 590 / 599**,WS-04 **55/55 全绿**。
    `600` 这个**点**被钉住了,**600 以下整条区间没有**。

    **修法**:补**受控下沿**断言 —— 用 `createPetRecord('mob_sheep', 1)` 把
    `lastProduceAt` 钉成 1,于是 `tickRanch(_, 600)` 的 elapsed 恰为 **599**。
    上沿(599 不产出)+ 基准(600 产出)+ 越界(601 不产出)合起来,周期值被**双向钉死**。
    修后我在真仓库复跑值域扫描:`2/10/100/300/500/590/599/601/607/1200` **全部变红**。

    **推广**:凡验收标准写「改成荒谬值必红」,都要问一句:
    **「荒谬」是一个点还是一个区间?** 正确的执行方式是**值域扫描**,
    并且**两侧都要扫**(往大改 + 往小改)。只往一个方向改,只能证明单边。

19. **「插入式」故障注入会静默失效 —— 后者胜**(本轮实测,Lead 亲踩)
    —— 我给 `WS-14` 做故障注入时,用「**在目标方法定义之前插入一个同名方法**」
    的方式模拟回退:
    ```ts
    /* 插在真 `feedStationAt` 之前 */
    feedStationAt(..._a: never[]): number { void _a; return 0; }
    ```
    结果 **8/8 全绿**,我一度以为「这条断言没有区分力」。
    真因:类体里出现**两个同名成员,后者胜**,真实现把注入覆盖了。

    **⇒ 故障注入优先用「改名 / 删调用 / 改字面量」,它们与既有定义互斥。**
    若必须用插入式,**先确认不会与既有定义重名**。

    **推广**:这条与陷阱 15(「写坏文件也能让它红,但那是解析失败,不构成证明」)
    是**同一族**的:**注入本身没生效,却被当成验证通过**。
    与另两条同族:**17(判定「谁引用谁」必须共用一套词法)**、
    **18(任务书表格会错)**。四条都在说同一件事 ——
    **验证动作本身的正确性,和被测对象的正确性一样需要被验证。**

20. **写「不严谨的探针」会连出三次相反结论 —— 先怀疑测量,再怀疑缺陷**(本轮实测)
    —— 复核 `task-46`(传送带货被摧毁)时,我连续得出**三个错误结论**,每个都是探针错:
    1. 装载后**立刻**测基线 —— 带内货存在私有 Map,**投影要等慢帧**,故读到 0,
       我判「货丢失」
    2. 跑 1 帧仍不够 —— 慢帧在 `frame % FAST_PER_SLOW === 0`,需跑满 10 帧
    3. 反复调 `setGroundItems` —— 它是 `this.mobGround = items`,**整体替换**语义,
       把我上一次落到地面的货抹掉了,于是我报「吞了 2 件」
    三次同一个病:**没读 API 就假设语义。**

    **根因是一条缺失的可观测性**:带内货原先不投影到件表,于是
    **「货在带上等着」与「货被销毁」从外部看完全一样**。
    这让**任何人都无法自证是探针错还是缺陷存在** ——
    ⇒ **可观测性不是「显示好看」,是「让人能自证」的能力。**

    **顺序纪律**:得出「缺陷存在/不存在」的结论前,先问
    **「如果我的探针错了,会看到同样的现象吗?」**

21. **白名单能否静默掩盖可达模块?——实测结论:不能**(本轮实测,已确认安全性)
    —— 这类「登记表」有一个隐蔽的攻击面:**往豁免表里加一行,就能让一个真可达的
    模块从「可达」统计里消失**,且没有任何门禁会响。
    实测:把**必然可达**的 `server/src/sim/world_sim.ts` 插进 `UNREACHABLE_EXEMPT`,
    门禁**立刻红**,且**可达/不可达数字不受影响**(仍 60/22,只多一行白名单)。
    ⇒ **门禁查的是「白名单条目是否真的不可达」,不是「白名单有几条」。**
    这个性质值得为所有「登记 + 理由」式表结构照做一遍。

22. **`setGroundItems` 是替换而非追加**(本轮实测)
    —— `world_sim.ts` 的 `setGroundItems(items)` 实现是 `this.mobGround = items`,
    **整体替换**。反复调它会把之前落到地面的掉落物**抹掉**。
    计数的测试若反复调它做「喂料」,会得到凭空少掉的数字。

23. **「句法相同、语义不同」的东西不能靠句法扫描器区分**(本轮实测,我连错两版)
    —— 我为「校验通过但无执行」这类缺陷写门禁,连错两版:
    - **第一版**:要求 `if (!v.allowed)` 的**体为空** ⇒ 实测 0 命中。
      真因:真实形态是体**非空**(里面 `client.send('reject')` 处理**失败**),
      空的是**成功侧**。我把「处理失败」误当成「有执行」。
    - **第二版**:要求 handler 体**恰好 1 条语句** ⇒ 仍 0 命中。
      真因:体是 **2 条**(`const v = ...` 取判定 + `if (!v.allowed) ...` 只处理拒绝),
      而我的闭合行过滤把 `});` 留下了。

    收紧到「N 条 `const` 声明 + 恰好 1 条拒绝守卫」后,命中 3 个 —— 但**含 1 个误报**:
    `move` 与两个真缺陷**句法逐字相同**,它的 `applyMove` **含真状态赋值**
    (`p.x = intent.x` 等)⇒ 执行完成于调用内,不是缺口。

    **⇒ 差别是语义,不是句法。** 硬报就产生误报,而本仓记着
    「**一条会误报的门禁等于没有门禁**」。

    **最终设计**:句法扫描只负责**发现形态**(可靠),人的判定写进登记表并**附可复核证据**,
    门禁负责**强制登记 + 漂移检测**(修好了会报「应移出」)。
    ⇒ **这一版的诚实之处是:它不宣称「自动发现缺陷」,只宣称「不让你悄悄漏掉」。**

    **推广**:凡判据想用「代码形态」去推断「行为」,先问一句
    **「语义相同但形态不同的、形态相同但语义不同的,各有几例?」**
    两类都实测过再决定判据能表达什么。**表达不了就别假装能。**

24. **门禁自检脚本自己崩掉,比它静默跳过好**
    —— 我给 T37 插用例时漏了一个尾逗号,`gate-selfcheck.ts` 直接 `SyntaxError` 起不来。
    这看着是失误,实则**是正确行为**:它没有把「用例没跑」伪装成「用例通过」。
    反例是我第一版注入脚本按 4 空格写锚点而表里是 2 空格,它打印
    「锚点不唯一,跳过」然后**继续执行并报告 0 个失败** —— 那才是危险的。

25. **注入器必须带「生效自检」—— 光改锚点写法不够**(`build-wiring` 实测,源自陷阱 19)
    —— 它踩到与陷阱 19 **同一条**(插入式注入被同名键静默覆盖,跑出假绿),
    但补了一层我没想到的防护:**注入后核对运行时取值真变了**;
    没变就判 **「注入无效」**,并与 **「断言查不出」严格区分**。

    加了自检后**立刻又抓出另一条**(改代码逻辑、数据摘要看不出)——
    ⇒ 说明「陷阱 19 的修法(换锚点写法)」**只解决了一半**:
    真正的通用修法是**每次注入都自证已生效**,而不是依赖锚点选型。

    **推广**:这与陷阱 15(写坏文件也能让它红,不构成证明)是**同一族的一体两面**:
    前者防「假绿」,本条的「生效自检」防**「假红」**。
    ⇒ **注入的两种失败(没生效 / 只是解析失败)都必须显式判掉,才能把颜色当证据。**

    **补充(本轮实测,第 4 种注入失效模式):「换行风格」**
    —— `build-wiring` 的 I1/I2/I3 首轮全部报「**锚点未命中 0 次**」,
    因为 `server/src/sim/world_sim.ts` 是 **CRLF** 而它的锚点字符串是 **LF**。
    若没有生效自检,这 3 条会被读成「注入生效但断言查不出」
    ⇒ 得出「**断言没牙**」的结论,而真实情况是「**注入根本没进去**」。
    **颜色与结论完全相反。**

    ⇒ 失效模式现已四种:①插入式被同名键覆盖(陷阱 19)
    ②锚点多重命中(改到非目标处)③改代码逻辑但数据摘要看不出(陷阱 25 本体)
    ④**锚点与源文件的换行风格不一致**(本条)。

    判据:锚点字符串**尽量不要手写多行字面量**,而是**从文件里读出来再改**
    —— 我自己的注入器(`REFLECT_RADIUS` 那次)就是这么修的。
    本仓的 CRLF 面很广:**`world_sim.ts`、`verify.ts` 均为 CRLF**。

26. **「同一概念在两个地方独立长出来」——本仓已见三例**(本轮实测)
    —— 一个概念缺口如果**不是笔误而是视角缺失**,它会在**互不相干的地方各长一次**:
    | 概念 | 长出来的地方 1 | 长出来的地方 2 |
    | :--- | :--- | :--- |
    | `scripts/**` 算不算生产侧 | `orphan-audit.ts` 只扫 `server/src`+`client/src` | `verify.ts` `findFileByName` 只搜 4 个目录 |
    | 白名单条目能否跨行 | `verify.ts` **支持**多行理由 | 两个消费者各自假设「不能」 |
    | 【本轮】 | 我改成多行 | `gate-selfcheck` 计数漏 3 条 ⇒ 假失败 |

    **⇒ 修一处不够,要问「这个概念还有谁在假设它?」**
    第一个例子是**同一疏漏**(漏了 `scripts/`);
    第二个是**同一假设的两次独立复兴**(两处都以为语法是单行的)。

    **实践判据**:当一个 bug 的根因能写成一句**概念性的**话
    (而不是「这行写错了」),先全局 grep 那个概念,再决定改几处。

27. **「接口可达」与「端到端闭合」是两件事 —— 数字的**语义**要和事实同强度**(本轮实测)
    —— 我摘白名单时说「可达 60→62」,而实测(用 `verify.ts` 自己的 lexer):

| 方案 | 代价 | 评价 |
| :--- | :--- | :--- |
| (a) 把图集提交进仓库(`client/public/`) | +2.1MB 二进制进 git | **推荐**:2.1MB 对现代仓库可接受,且让「克隆即可构建」成立。可用 Git LFS 或接受体积 |

> 本节记录本轮最重大的发现 —— 它不是某一个 bug,而是**一类反复出现的形态**。

### 两个方法论收获(来自 `coop-party` 的自查)

1. **多人并行下,绝对红绿判定等于没判定。**
   它的自检用例原本断言「注入后 verify 应该红」,但队友改了 `WS-10.test.ts` 让基线**自带红**,
   于是「红」不再能区分「本用例抓到了」还是「别人弄红的」。
   修法:改用**差值判定**(只算本用例新引入的 ✗)。
   > 这条解释了本会话里我自己也差点误判的一次:我把队友的在改中状态当成了我的问题。

2. **一个「0」可能是分类顺序的产物,不是测量结果。**
   可达性台报「等裁决 0」,读起来像「没有等人拍板的事」,
   实际是**35 条全都满足「等裁决」句式,却全被更具体的桶先抓走** ——
   改一处正则它立刻变成 2。
   修法:装「影子数」把成因暴露出来,而不是修改分类去迁就。

### 同期的第三个发现:白名单理由会过时

16 条 `client/**` 白名单的理由都写着「**本仓无装配入口**」,
而 `client/index.html` 与 `client/src/main.ts` **都存在**。
理由是**假的**,门禁全程绿色。

现有自检抓「文件不存在」「已可达」,**抓不到「理由本身过时」**。
`coop-party` 补了 `detectStaleReason()`:抓两类 ——
(1) 否定式存在断言(理由写「无 X」而 X 已存在);(2) 理由里引用的路径必须存在。

**它把局限如实写进了文档**:这不是自然语言理解,抓不到「字面仍成立但语义已变」。
补网方向是**把理由写成可判定的形式**,不是把正则写更宽 ——
**宽正则会误判正确理由,让人开始无视告警,比没有更糟。**

    但那是解析失败,不是行为失败,**不构成测试有牙的证明**。
14. **注入前先备份、还原后要复验** —— 本次一度把注入后的坏版本存成了 `.bak`,
    导致「还原」还原了坏文件;靠 `/tmp` 的另一份才救回。**验证:还原后再跑一次基线。**
