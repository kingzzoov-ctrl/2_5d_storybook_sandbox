### [CR-15] 2026-11-12 Lead — Boss 战利品自反馈闭环 + `loot` 类型表达力不足(7 处偏差 / 4 个 Boss)

**触发**:owner 的两个待决项之一 —— `BossDef.loot` 类型。配方「任意染料」那条另立 CR-16。

**它掉自己的祭品。** 这是 8 个 Boss 里**唯一**的自反馈(扫 `loot ∩ summonItem` 只命中它)。

实测取证:

| 判据 | 实测结果 |
| :--- | :--- |

> ⚠️ **措辞硬约束**:U2-a **不是**「已修复」。台账与文档里都不许用「修复」描述它。

> 移速上限**仍然**会随客户端声明抬到约 3.19 倍基线,绕过装备前置**仍然**成立。

**口径陷阱(别把两个上限搞混)**:真正约束**持续**速度的是「窗口均速」那条
(`cap = BASE × sanitizeMul(speedMul) × speedWindowTolerance`);

—— 单帧口径折算约 18.36 格/秒,比窗口口径宽松,拿它当「上限」会高估。

**影响面**(需同步改动的 WS):
- 需 WS-07 定义**产出凭证账**(按 tick 记合法来源)与**权威物品总量**
  (`repo.ts:631 totalItemsOf` 已有,缺的是「无 db 时的降级路径」);
- 需 `PlayerState` 增**装备槽**(目前只有 `weaponId`)才能做服务端移速核算;

**建议改法**:
1. 网络层**不信任客户端**:`allowedSources` / `capacity` / `beforeTotal` 改由服务端状态导出
   (`playerState(...)` 已取到,只是被 `void` 掉了);

4. U2-a 二选一:改注释(承认不自证)或真做服务端核算。

## U2-b — 复核中发现的新真缺陷,已修

**非数字声明会让钳位公式产生 `NaN`**
(`Math.max(0, {})` = `NaN`),而 `dist > NaN`、`since < NaN` **恒为 false**
⇒ **瞬移 / 窗口均速 / 攻速三道检查同时静默失效**,单帧跳 200 格被**直接放行**。
`{"speedMul":{}}` / `{"speedMul":"abc"}` 经 JSON 反序列化即可到达 `onMessage`
(TS 的 `speedMul?: number` 不产生运行时校验)。此缺陷**与「上限多大」无关**,与 U1 同类
(判据本身被污染),严重度高于 U2-a。修法:加 `sanitizeMul`,非数字 / `NaN` / `-Infinity`
兜底为「未声明」(`+Infinity` 本就正确钳到上限,不动)。
行为级验收 5 用例:单帧瞬移、窗口均速、攻速、**真实入口 `applyMove`/`applyAttack`**、口径一致
—— **修复前 140/144(4 红),且回退行为后重新变红,已验证**。

**本版复核**(2026-11-12):`{}` / `"abc"` / `null` / `undefined` / `NaN` / `-Infinity`
六种非法声明经 `maxDisplacementPerTick` 全部返回 `0.36`(即兜底为「未声明」),**无一产生 `NaN`**。

**第三部分:新增生产可达性门禁(系统性对策)**

前面 7 例中,**第 5/6/7b/7c 例都是靠人工 grep 才发现的**。一次性对策:

`scripts/verify.ts` 新增 `checkReachability()`,以 `package.json` 真实入口为

✓ 生产可达性:可达 23 / 不可达 51 (共 74,入口 2 个,白名单 51 条)

1. **默认告警**(不是 fail):不可达有合理情形(本仓**无客户端装配入口**,

2. **数字可断言**:输出带完整计数,任何一位变化都可察觉。
3. **`--strict-reach` 开关**:把「未登记的不可达模块」升级为失败,实测退码 1。

**白名单 51 条**按目录分组、逐条写理由。四类失真自检全部生效:
文件不存在 / 理由过短 / **已变成可达**(过时条目)/ 生产入口不存在。

> 生产侧**从未注入具体驱动**。已改正为「尚未注入」。

**第四部分:注入类操作的安全教训(三方都踩了同一形状的坑)**

「不可重入的副作用不该藏在别人的流程里」,本轮三人各自踩了一次:

3. Lead:注入脚本第二次 `restore` 时**备份已被第一次消耗** → `room.ts` 一度留在注入态。

**第八部分(补记):两条验证方法论**

**1. `eq` 抛错导致同 test 后续断言不执行 —— 连续两次命中**
`harness.ts:162` 的 `eq` 失败即 `throw`。于是「注入后某条断言没变红」可能**只是它没被执行**。

实测两次:
- `WS-06:553` 在 `:552` 之后,前者先 throw ⇒ 误判「未修复」;**交换两行顺序**后才证明它变红。
- `WS-01:679/680` 在 `:664` 之后 ⇒ 误判「无牙齿」;**中性化 `:664`** 后才证明它们有牙齿。

> **规范(S30)**:凡验多条断言,必须用「**交换顺序**」或「**中性化前驱**」独立证明。
> 否则会把**有牙齿**误判成**无牙齿**,产生假缺陷。

**2. 恒真断言 ≠ 覆盖缺口**
`WS-01:740` 的 `eq(x, OBSIDIAN_ID)` 确属同义反复(注入 110→999 仍绿)。
但同 test 内另有 `:679/680` 用**字面量 110** 守住同一行为 —— 经中性化前驱验证**确会变红**。

> **判据(S32)**:恒真只在**无处覆盖**时才是缺陷。判定顺序 =
> 先查同套件有无字面量锚定 → 再定性为「冗余噪音」还是「漏检风险」。
> 报成「WS-01 有缺陷」会**冤枉 317 条断言里健康的 316 条**。
>
> **复核者的结语(采纳为原则)**:本轮最有价值的单条发现不是任何一个缺陷,
> 而是这条判据 —— 因为它避免的是**冤枉**。
> **找缺陷是本事,不给健康代码扣帽子同样是。**
> 一个只会「报出问题」的审计者,会把健康代码当成缺陷来「修」,
> 而那种修改本身就是新的缺陷源(G3-1 的 `AREA_TOO_SMALL` 一例即此:
> 若按先验报「建议删除」,owner 会删掉一个正常工作的拒绝码)。

**3. 同一常量在同一套件内可「两种性质并存」**
`WS-06::ICON_SIZE` 注入 16→8 ⇒ `61/61 → 49/61`(12 红),但:
- `:111/112` 查 `SILHOUETTE_ART` **字面量美术** ⇒ **变红**,有牙齿
- `:552/553` 查 `prompt.ts:144 minItems: ICON_SIZE` ⇒ **仍绿**,真同义反复

门禁白名单键是 `(套件::常量)`,只能报一条 —— **这是固有粒度局限,不是漏报**。
只说「有牙齿」会漏掉真缺陷;只说「同义反复」会冤枉 111/112。**两者并存,都要说。**

### (1) `FROM_NOTHING`(凭空产出)可绕过

`checkInventory:382` 判 `!input.allowedSources.has(op.source)`,
而 `allowedSources` 的取值**来自客户端报文**。行为验证:

```

伪造产出凭证 → 通过(凭空获得物品)
```

前提先证过,所以这道检查**不是装饰,是真被绕过了**。

### (2) `OVERFLOW`(容量溢出)可绕过

`capacity` 同样客户端自报:

```
capacity=<小值> → 拒绝(OVERFLOW 分支正常触发)
capacity=<任意大值>  → 通过(该分支放行)
```

> ⚠️ **我自己在这里踩过一次坑,如实记录**:第一版探针用 `delta=+100`,
> 被 `BURST`(单帧净变化上限)**抢先拦下** ⇒ 我差点得出

> **教训**:一个检查「通过了」可能是被**另一道检查**拦下的假象 ——
> 必须确认命中的是哪一条拒因码。

### (3) `NEGATIVE`(消耗不存在的东西)恒不可达

L184 的算法把「待扣减量」当作「已有总量」:

```
beforeTotal = Σ max(0, -delta)
after = beforeTotal + net
```

- 全为扣减:`net = -Σ|delta|`,`beforeTotal = Σ|delta|` ⇒ `after ≡ 0`
- 全为产出:`beforeTotal = 0`,`net = +Σdelta` ⇒ `after = +Σdelta`

**实测 4 组全部 `after >= 0` ⇒ `ITEM_NEGATIVE` 分支不可达。**
对照:若 `beforeTotal` 取服务端真值(实际只有 10 件却想扣 50)→ 正确拒绝 `ITEM_NEGATIVE`。

**背景(为什么做这件事)**:本轮目标是「做好底座」。持久化层有最贵的一类返工陷阱:
**测试替身与生产引擎语义不同**。`WS-07` 的 109 条测试全部跑在 `memory_db.ts` 上,
而生产用 SQLite —— 两者若不一致,内存全绿、上线翻车。

**第一部分:`SqliteDb` 是 169 行死代码**

`driver.sqlite.ts` 的 SQL 翻译逻辑**从未被任何测试执行过**:`better-sqlite3`
是 `optionalDependency`(默认不装),所有测试走 `MemoryDb`。
文件头那句「换驱动(如 `node:sqlite`)只需再写一个同接口实现」也从未被验证。

**改法**:把连接层抽成 `SqlConnection { exec, all, get, run, transaction, close }`,
`SqliteDb` 只保留 SQL 生成/白名单/绑参/BLOB 归一 —— 于是两个引擎共用同一份翻译层:

| 能力 | `better-sqlite3` | `node:sqlite` |
| :--- | :--- | :--- |
| 设 PRAGMA | `db.pragma()` | 只能 `db.exec('PRAGMA ...')` |
| 事务 | `db.transaction(fn)` | 无,手写 BEGIN/COMMIT/ROLLBACK |
| BLOB 读回 | `Buffer` | `Uint8Array` |
| 绑 `boolean`/`undefined` | 报错 | 报错 |

两个适配器分别约 15 / 25 行 —— **「薄适配器」从注释变成实测值**。
`node:sqlite` 是 Node 24 **内置**,因此 SQL 路径现在零依赖可跑,
`openNodeSqlite()` 让生产部署不装 `better-sqlite3` 也能跑。

**第二部分:`MemoryDb` 与真实引擎有 7 项语义分歧(实测)**

`schema.sql` 有 **70 个 NOT NULL + 27 个 CHECK + 26 个 DEFAULT + 11 个外键 + 1 个触发器**,
改前 `MemoryDb` **一条都不强制**(只查主键冲突)。用 `node:sqlite` 的真实引擎逐项对照:

| 场景 | 改前 `MemoryDb` | 真实 SQLite |
| :--- | :--- | :--- |
| 插入指向不存在父行的子行 | 接受 | 抛 `FOREIGN KEY` |
| 插入缺 NOT NULL 列 | 接受 | 抛 `NOT NULL` |
| `update` 把 NOT NULL 写成 null | 接受 | 抛 `NOT NULL` |
| CHECK 写非法值(`role`/`access_mode`) | 接受 | 抛 `CHECK` |
| 改 `rooms.status` | 不写审计事件 | 触发器写 `ROOM_STATUS` |

**改法**:约束**从 DDL 解析**(硬编码会与 `schema.sql` 漂移,而漂移本身就是这次要修的病)。
新增 `parseCheckExpr` / `checkPasses` / `unsupportedChecks()`;`insert`/`update` 走
`enforceConstraints`;`applyTriggers` 模拟 `trg_rooms_status_change`。
实测结果:**10 项对照全部一致,7 项分歧归零**,且 923 条既有断言仍全绿
(说明生产代码本来就在写合法数据 —— 修的是替身,不是业务)。

无法解析的 CHECK 形态(`access_mode = 'PUBLIC' OR password_hash IS NOT NULL` 这类跨列表达式)
由 `unsupportedChecks()` **显式暴露**,不静默放行 —— 静默放行才会让门禁变装饰。

**第三部分:顺带修掉两个真 bug**

1. **`splitStatements` 不跳过 SQL 注释**。`schema.sql` 的注释头里含 `;`
   (「见 repo.ts:savePlayer」这类说明),于是 `CREATE TABLE` 被从注释中间切开:
   实测 **9 张表只解析出 2 张**,而 `migrate()` 不报错 —— 表结构解析静默失效。
   修法:切分时跳过 `--` 行注释与 `/* */` 块注释。

### [CR-11] 2026-11-11 Lead — 关闭 U3(前提为假)+ 接通交互/受击:9 种事件原本永不发生

> 事件是否要持久化/重放 | 回放系统若要做,需先定事件的可序列化边界(**suppress 闭包**)

| :--- | :--- |

但生产路径从不经过。

这是本项目**第四次**「子系统完整实现、单测全绿、编排层不接」:

| 第几次 | 部件 | 症状 |
| :--- | :--- | :--- |
| 1 | 25 个 AI 的 `tick` | 生产调用 0 次 |
| 2 | `fsm.tick()` | 22/24 生物永远站着 |

1. 「交互/受击可达」—— 判据是 `interactHits > 0 && damageHits > 0 && 种类增长`;

### [CR-10] 2026-11-11 Lead — 举投系统在生产不可达:一份空 Map 吞掉了 WS-02

`docs/SIM-orchestration.md` US8

**问题**:`SIM-orchestration.md` US8 写的是「`CarrySystem` 已构造但未接入循环,
`tick` 未被调用」。实测发现它比描述的更严重 —— **整个举投系统不可达**:

```ts

```

| 观察 | 结果 |
| :--- | :--- |
| `world_sim.ts` 里 `this.carry.xxx()` 调用点 | **0 个** |
| 世界里 2 个玩家 → `carry.actors.size` | **0** —— 玩家从未进入 |
| `s.lift('a','b')` | 不存在这个入口 |
| `CarrySystem` 自身可用吗 | **完全可用**(直接 `new` 后 `tryLift` 返回 `OK`) |
| WS-02 断言 | **43/43 全绿** |

这正是本项目第三次出现同一类缺口:**子系统完整实现、单测全绿、
编排层从不调用**。前两次是「25 个 AI 的 `tick` 生产调用 0 次」
和「`fsm.tick()` 生产调用 0 次 → 22/24 生物永远站着」。

WS-02 全绿却不可达,原因是它直接 `new CarrySystem(map)` 测,
**从不经编排层** —— 单测的绿色只证明「carry 自己能跑」,
不证明「世界里能举起人」。

**为什么是空 Map 而不是漏注册**:构造时根本没有 body 可注册 ——
`CarryActor = { body: DynamicBody, shield: boolean }` 包装的必须是
**与物理同一份** `DynamicBody`。若注册时各存一份,则:
- 举起的 `z`、释放时的速度写回哪一份?
- 物理自己 `spawn` / `bodies.delete`(玩家注册、生物生成、卸载)时,两份表永远追不齐。

**决策:活视图(`carryActors()`)而不是双份 Map**

```ts
private carryActors(): Map<string, CarryActor> {
  const bodies = this.physics.bodies;      // 同一份,不复制
  // 只覆盖 get/has/size;缺失的 id 返回 undefined(与真实 Map 语义一致)
}
```

依据:`CarrySystem` 对该表只做 `get()`(实测 **13 处全是 get**,
无遍历、无增删),所以只实现读路径就够,且不会有「看着能写实际不生效」的假象。

**同时补上的三个入口**(此前一个都没有):

| 方法 | 语义 |
| :--- | :--- |
| `lift(carrierId, targetId)` | 举起,返回 `CarryReject`;主动交互,不是每帧试 |
| `dropTop(carrierId)` | 放下链尾(不投掷)—— 与投掷分开,因为放下应保持站立 |
| `throwPlayer(carrierId, dx, dy, mul)` | 投掷,返回初速度,由物理后续帧积分 —— **不在这里写位置** |

**投掷一次之后永久不能再投** —— 而 `cooldown` 是私有 Map,从外面看不出异常。
放慢帧是因为冷却常量以秒计,2Hz 的 `dt=0.5` 同量纲。

**验收**(经编排层,不经 carry 单测):

### [CR-9] 2026-11-11 Lead — 移动权威裁决:22/24 生物原本永远站着

**范围**:`server/src/mobs/host.ts`、`scripts/verify.ts`、
`tests/WS-FND-02.test.ts`、`docs/EVENT-BUS.md` §3/§7、
`scripts/backlog.ts`(新增)

**问题**:`EVENT-BUS.md` U1 标为「阻塞:移动权威待决(三方案 A/B/C)」,
且文档倾向 A。**实测发现它不是设计选择,而是活着的功能缺失。**

测量(每只生物单独放一个宿主,跑 120 慢帧 = 60 秒):

| 观察 | 结果 |
| :--- | :--- |
| 位移 > 0.5 格的生物 | **1/24**(仅 `mob_sky_manta`,它的 AI 自己写位置) |
| 与玩家在场与否的关系 | **无关** —— 22 只无论有无玩家都不动 |
| `fsm.tick()` 单独跑 120 帧 | 闲逛 **5.44 格**;玩家 3 格外时追猎到攻击距离 |

根因:宿主**绝不调用** `fsm.tick()`(原设计怕「两个移动权威」),
而**游荡逻辑只存在于 FSM 里** —— 于是 22 种生物连游荡都不会。

**为什么 A/B/C 都不选**(这也是裁决依据):

| 方向 | 实测否决理由 |
| :--- | :--- |
| A. FSM 接管全部移动 | 要删 AI 的 7 处位置写入,而它们是**专属运动**(野猪直线冲锋、穿山甲翻滚、蝠鲼参数化滑翔、史莱姆跳向甜莓),交给 FSM 就丢特色(违反 LEAD-PLAN 风险 R2) |
| B. FSM 退化为纯状态机 | 要删 steering —— 实测 `fsm.ts` 里 `steer` 24 次、`probe` 19 次、45° 避障 15 次,那是 WS-04 的核心产出 |
| C. 双写同步 | 保留 steering 却不能用它移动,属「都不选」的中间态 |

**决策(方案 D)**:按**动作类型**分工,而不是按「谁拥有移动权」二选一 —

1. FSM 先算基础移动(游荡 / 警戒 / 追猎),带 45° 避障,写进 `rt`;
2. AI 随后 `tick`;
3. AI **写了位置**(与 FSM 落点差 > `1e-6`)→ 以 AI 为准,并把 FSM 内部位置**同步**到 AI 落点;
4. AI **没写** → FSM 的位移留下。

判据是「AI 有没有写位置」而非「AI 属于哪一类」:新增 AI 无需注册。

**效果**:

| 指标 | 改前 | 改后 |
| :--- | ---: | ---: |
| 会动的生物 | 1/24 | **22/24** |
| 无玩家时位移 | 0.00 格 | 1.80 格/60 秒(游荡) |
| 有玩家时位移 | 0.00 格 | 最高 15.31 格/60 秒(追猎) |

**同步那一步不是美化**:故障注入(去掉 `rt.fsm.x/y = rt.x/y`)立刻报
**位置分叉 4.5** —— 两条轨迹越走越远,表现是**生物瞬移**,比「生物不动」更难查。
所以不变量是「调用之后位置不分叉」,而不是「不调用」。

**顺带修掉的两个既有缺陷**:

### [CR-8] 2026-11-11 Lead — 流体迭代顺序:修「扩散速度随世界面积急剧变慢」

**范围**:`server/src/world/fluid.ts`、`server/src/sim/world_sim.ts`、
`scripts/verify.ts`、`tests/WS-01.test.ts`、`docs/SIM-orchestration.md`(US4)、
`docs/FLUID-BUDGET.md`(新增)

**问题**:`docs/SIM-orchestration.md` §10 US4 的诊断是**错的**。它写:

> **流体预算在大世界偏低** — 1024 格/慢帧,512×512 世界铺满需 128 秒。
> 建议按玩家距离加权或提高预算。

实测推翻了「预算偏低」:

| 世界 | 每步耗时 | 占 500ms 慢帧预算 |
| :--- | ---: | ---: |
| 512×512 | 0.99 ms | **0.2%** |
| 1024×1024 | 3.9 ms | 0.8% |

CPU 完全不是瓶颈(空/有 = 99%,说明成本几乎全是固定开销)。
真瓶颈是**覆盖延迟**:纯游标轮询下,一格被访问的间隔 = `n / budget` 慢帧。

| 世界 | 水从 y=2 铺到 y=27(修复前) |
| :--- | ---: |
| 64×64 | 39 秒 |
| 128×128 | **2268 秒(38 分钟)** |
| 256×256 | 超过 2500 秒未收敛 |

原因是水的**前沿**每帧最多推进 1 行,而前沿所在行要等轮询转到才被处理;
世界越宽,一帧覆盖的行数越少(`budget / width`:64→16、128→8、512→**2**)。

**提高预算治不了它** —— 调到 4 倍只是把 128 秒变 32 秒,而每帧成本线性上升。
瓶颈是**访问顺序**,不是预算大小。

**决策**:

1. **活跃格优先 + 游标补齐**:维护「有水的格 + 四邻」的活跃集合,每帧先处理它,
   剩余额度给游标。水的边缘总被尽快推进,静止的水由游标兜底。
2. 活跃集合用**轮转数组**,不是 `Set`(见下「最贵的坑」)。
3. 消除三处 O(世界面积):落账循环改遍历 `touched`;`phasePass` 只扫活跃格;
   `delta` 数组跨帧复用(原先 1024² 每帧分配 4MB)。
4. 顺带删除 `fluxEdge` 的 `vertical: boolean` **死形参** —— 它在函数体内
   一次都没被读,而文件头设计说明却声称「向下优先(重力满流量),水平按位势差
   减半扩散」。核查手册 L20 后确认手册只要求「元胞自动机流淌扩散」,
   没有规定重力优先,故删形参并让文档改口(重力实际由 `elev` 层差表达)。
5. `FluidStepReport` 增加 `visited` / `active` 两个诚实字段 ——
   `processed` 名为「已处理」实则计「遍历额度用量」,全干世界也报满额,
   会掩盖问题(实测空世界 `processed=1024, moved=0`)。

**效果**:

| 世界 | 修复前 | 修复后 |
| :--- | ---: | ---: |
| 64×64 | 39 秒 | 28.5 秒 |
| 128×128 | **2268 秒** | 32.0 秒 |
| 512×512 | >2500 秒 | 31.5 秒 |
| 1024×1024 | 未测 | 32.0 秒 |

单步成本:1024×1024 稀疏场景 **3.026ms → 0.120ms**(25 倍)。

**最贵的坑**:活跃集合最初用 `Set`,按插入顺序遍历。水铺平后集合有 1160 格
(> 预算 1024),此时在空地注入 500 毫格新水 —— **`moved` 恒为 0、水原地不动**
(5 帧内邻格毫无变化)。新格插在 1160 个老格之后,`done >= limit` 已成立,
它永远轮不到。**这不是平衡,是停顿**;两者在 `moved === 0` 时表现相同,
必须靠「在空地注水看它是否立刻流」区分。改用轮转数组 + 位置索引后修复。

**验收**:`WS-01` 44 → **48** 条;`verify.ts` 集成 24 → **46** 条
(新增「流体扩散与世界面积解耦」「流体守恒 300 帧」「上报字段诚实」
「文档与代码一致」「非 WS 文档有实质内容」「文档链接有效」);

### [CR-1] 2026-11-10 Lead — `eq()` 对数组/对象用引用比较,导致「期望=实际却报红」

- **文件与符号**:`shared/testing/harness.ts` → `eq<T>(actual, expected, msg)`
- **原因**:现实现为 `if (actual !== expected)`,对**数组与对象**是引用比较。两个内容相同的数组必然 `!==`,断言失败;而报错信息 `String(expected)` / `String(actual)` 会把两边打印成**完全相同的文本**:

  ```
  ✗ [WS-09] LOD 合并:... — 合并边长 期望 1,2,4,8 / 实际 1,2,4,8
  ```
  这类失败有极强误导性 —— 看上去像环境问题,实际是测试桩缺陷。已实际咬伤 **WS-06**(`F1` 数组比较)与 **WS-09**(至少 4 条:合并边长、合并因数、外接框、越界音高)。全仓 `eq(` 调用点 1271 处,其中含数组字面量的调用均处静默失效风险。
- **影响面**:全部 11 个 WS 的测试文件。**只影响测试桩,不影响任何实现代码或冻结契约**(签名不变,新增可选行为)。
- **建议改法**:保持 `eq` 签名与调用兼容,内部对 `object` 类型走**结构化等价**比较:
  - 原始类型(`string`/`number`/`boolean`/`null`/`undefined`/`bigint`/`symbol`)仍用 `!==`,行为零变化;
  - 数组按**长度 + 逐位**比较(递归,支持嵌套与非原始元素);
  - 普通对象按键集合 + 逐值比较(递归);
  - 报错信息改用**结构化打印**(数组打印为 `[1,2,4,8]` 并显式标出**首个不相等的位置与两侧值**),避免「两边看起来一样」。
  - `Map`/`Set` 按元素集合比较;`NaN` 视为相等(`Object.is`);循环引用用已访问集防爆栈。
- **兼容性论证**:所有原本**通过**的原始类型断言仍通过;所有原本**通过**的数组同引用断言仍通过(`a === b` 时逐位必等);所有原本**失败**的数组断言,若内容确实相等则转为通过(**这正是缺陷**,属修复),若内容不等则仍失败但**报错信息更精确**。因此不存在「把真失败改成通过」的风险 —— 逐位比较比引用比较**更严格**,不会放过任何内容不等的数组。
