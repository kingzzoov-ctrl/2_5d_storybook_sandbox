## 2 推荐裁决(三条,我可逆地做)

### R1 世界重置是**宿主能力**,不是编排层自造
在 `room.ts` 的 `WorldSaveHost` 上加一个**可选**能力:

```ts
resetWorld?(opts: { seed: number }): { applied: boolean; seed: number; reason?: string };
```

- **可选**:不实现它的宿主(今天的 `WorldSim`)仍然合法 ⇒ 运行期走"能力缺失"分支;
- 动作层**不自己 `new` 一个世界**:那会让"谁持有世界"出现两个答案(编排层一份、宿主一份),正是本仓反复防的那类双份实现;
- 好处:`RESET_WORLD` 的**逻辑**(权限 / 参数 / 能力缺失 / 回执)今天就能接完并测完,剩下的是宿主那一半。

### R2 权限：`destructive` + **显式确认**
- 权限位就用既有 `:197` 的 `destructive`(不新造角色表,不弱化);
- 报文必须带显式确认(建议 `confirm: true`),缺失 ⇒ `INVALID` —— 破坏性动作**不许**因为"少写一个字段"就执行;
- 未知/多余字段不静默忽略(与 `START_PARTY` 的回声核对同一纪律)。

### R3 能力缺失 ⇒ **显式** `NOT_IMPLEMENTED`,不许静默成功
宿主没有 `resetWorld`(今天的生产就是这一种)⇒ 回 `NOT_IMPLEMENTED` + 可读理由,
与未知动作名同一条路。这一点是整个仓库的既有纪律:
"能力存在而通路缺失"必须**说出来**,否则下一次读代码的人会以为重置已经在工作。

## 3 实现边界(做完 R1~R3 之后仍然成立的"没做到")

即使动作层接完,今天**生产里仍然重置不了**:

1 **`worldSaveHost` 在生产是 `null`** —— 装配层那条路(`index.ts` 的 `createHost` → 交进房间)
   至今没有真调用者(这是既有的"B 路装配"欠账),所以 `resetWorld` 连"能力缺失"
   这一条都走不到,而是连宿主都没有;
2 就算宿主有了,**重放"造世界"这一步**不是小改:`WorldSim` 的状态来自构造期播种
   (~3000 行里的初始化路径),要"换一个种子重生"必须有一条**重建**路径,而不是改几个字段;
3 **客户端的旧世界**:换世界之后 chunk/实体/玩家坐标全是旧的,必须有一条
   "请重新握手 / 重拉快照"的下发路径(`net/room.colyseus.ts` 今天没有);
4 **存档政策未裁决**(见 §4)。

## 4 必须 owner 定的一件事:存档政策

世界被重置时,已有存档怎么办?三种都自洽,但行为完全不同:

| 选项 | 含义 | 后果 |
|---|---|---|
| **A 丢弃** | 重置 = 全新世界,旧地形不再可读 | 最"干净",但玩家昨天盖的房子永久消失 |
| **B 保留(换种子只换新区域)** | 旧 chunk 仍在,新种子只影响新生成 | 需要 chunk 级出处标记——**今天没有这个字段** |
| **C 归档** | 旧世界存成一份可回滚快照 | 需要存档表与配额裁决;今天 `rooms` 表只有元数据 |

我的推荐是 **A + 显式二次确认**(与 R2 同一纪律:破坏性动作要人明确按键),
但这**必须由 owner 定** —— 它决定玩家数据能否消失,不是我能替 owner 决定的。
