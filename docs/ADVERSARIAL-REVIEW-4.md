> **和第 3 批 G3-1 是同一个教训:扫描器的输出必须人工定性才能成为缺陷。**

### 2.7 两轮扫描的关系(避免误读)

本批有两个**独立**的注入轮次,不可简单相加:

| 轮次 | 候选来源 | 注入数 | 变红 | 全绿 | 全绿中的**真缺陷** |
| :--- | :--- | ---: | ---: | ---: | ---: |
| **A. S7 专项** | 静态三元组(`eq/near` 右侧确为被测常量) | 52 | 31 | **21** | **21** |
| **B. 剩余套件** | 各套件 import 模块的**前 10 个**数值常量 | 61 | 27 | 34 | **1** |

两轮在 WS-07 `PROTOCOL_VERSION` 上重叠(按一处计)。

**为什么 A 的全绿几乎全是真缺陷,而 B 的全绿几乎全不是**:

- A 的候选**已过静态筛选**(该断言右侧确实是被测常量)⇒ 注入全绿就说明该常量无约束力
- B 的候选**未过筛**,只是「该套件 import 的模块导出的常量」⇒ 多数套件根本不引用它

**这就是 §3.1 那个 34:1 误报率的来源**,也是为什么最终清单以 A 的 21 处为准。

### 3.1 WS-FND-05:10 项全绿,但**不是缺陷**

我第一眼看到「10 注入 0 变红」时判定为最差套件 —— **核实后推翻**:

```
WS-FND-05 在测试正文里对 CHUNK_SHIFT / DIRTY_WORDS / FLOOR_ID_MIN /
FLOOR_ID_MAX / FLOOR_BASE_COUNT / FLOOR_SLOT_MASK / FLOOR_UGC_FIRST /
FLOOR_UGC_LAST / FLOOR_UGC_ID / FLOOR_DEFAULT_MU 的引用数:**全部 0**
```

这些常量是**经由 import 的被测模块顺带进入我的候选池**,WS-FND-05 本身从不引用它们
(它测的是另外的东西)。**所以「注入不变红」完全正确**,不是假绿。

> 这是本次扫描暴露的方法论陷阱:自动候选池会用「套件 import 了哪个模块」
> 来推断「该套件负责哪些常量」,但这个推断是**过宽**的 —— 一个模块导出的常量,
> 套件可能一个都没测。**必须用「套件正文是否真引用」二次过滤**,
> 否则会把 4 个健康的套件误报成大面积假绿。

## 6. 建议(交 Lead 转发)

| 编号 | 对象 | 建议 | 写域 |
