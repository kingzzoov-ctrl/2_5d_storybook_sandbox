## 一、S26 起因:Lead 怀疑 R6 有同类「import 块带注释」问题

Lead 的判断依据是 S11 刚暴露的缺陷 A。**查证结论:那两个具体形态对 R6 都不成立,但查证过程中发现了一个新的真缺陷。**

### 1.1 「import 块里带注释」—— R6 **不受影响** ✓

R6 走的路径与 S11 不同:

```ts
const src = stripCommentsOnly(readFileSync(cur, 'utf8'));
for (const m of src.matchAll(/(?:from|import)\s+['"](\.[^'"]+)['"]/g)) { ... }
```

它**只取路径字符串,不切名字**,所以花括号里的注释不影响。

**静态扫 + 注入双重证实**:

| 检查 | 结果 |
| :--- | :--- |
| 生产文件里「import 块内含注释」 | **0 处** |
| 注入注释到 `demo.ts` 的 import 块 | 24/50 → 24/50,**无影响** ✓ |

### 1.2 ⭐ 但发现真缺陷:**幽灵依赖**

R6 用的 `stripCommentsOnly` **保留字符串内容**。于是任何**字符串字面量**里出现
`from './x.ts'` 都会被正则当成真依赖。四种形态实测**全部误抓**:

| 形态 | 代码 | 结果 |
| :--- | :--- | :--- |
| A 运行时错误消息 | `export const p = "failed from '../combat/damage.ts'";` | 24/50 → **26/48 误抓** |
| B 双引号包单引号 | `export const p = "src from '../a/b.ts' here";` | **误抓** |
| C 模板字符串 | ``export const p = `load from '../a/b.ts'`;`` | **误抓** |
| D 单引号内嵌 | `export const p = 'see from \'../a/b.ts\'';` | **误抓** |
| E 注释里(对照) | `/* from '../a/b.ts' */` | 无影响 ✓ |

**后果**:被误指的模块算作「可达」⇒ **不可达数偏小**。

**风险方向上分两种**:

| 幽灵指向 | 后果 | 危险性 |
| :--- | :--- | :--- |
| **白名单里的模块** | 该模块变「已可达」⇒ 白名单自检报失真 | **自我暴露** ✓ |
| **未登记的模块** | 它从未登记告警里消失 | **静默消失** ← 危险 |

> 这是**掩盖方向**的缺陷:R6 的存在意义就是「让不可达模块可见」,
> 而幽灵依赖恰好能让它**不可见**。比同义反复更严重 —— 同义反复让断言失效,
> 幽灵依赖让**审计本身失效**。

### 1.3 一个我必须更正的中间结论

排查时我的脚本一度报「现网 193 处幽灵」。**那是我的脚本错了**:真导入的路径**也在字符串里**,
我用「剥掉字符串」做对照,把真导入一起抹掉了,于是全部误判为幽灵。

**改成逐字符扫描代码态后:现网幽灵 = 0。** 门禁口径与代码态口径**都是 193 个相对导入,差 0**。

**所以:幽灵依赖是「机制真实存在、现网无可利用实例」的脆弱假设**,不是当前正在发生的错误。
我把这条更正写进报告,因为**未澄清的「193 处」会误导后续判断**。

## 二、修复:改用**代码态逐字符扫描**

新增 `extractRelativeImports(text)`,替换 `reachableClosure` 里的正则:

- 逐字符前进,遇到注释**整段跳过**
- 遇到字符串字面量**整段跳过内容**(这正是旧实现漏掉的)
- 只在**代码态**识别 `import` / `from` 关键字,再读紧随其后的字符串字面量作为路径
- 要求前一个字符不是标识符字符,避免 `myfrom` 之类误匹配

### 2.1 验收(三项判据全部通过)

| 判据 | 结果 |
| :--- | :--- |
| ① 四种幽灵形态**不再**误抓 | ✓ A/B/C/D 全部 24/50 无影响 |
| ② 真实 `import` **仍然**被抓(阳性对照) | ✓ 侧效用 import 与具名 import 均 24/50 → 26/48 |
| ③ **现网结论不变** | ✓ 修复前后都是 24/50 |

**判据 ③ 最关键**:修复若改变了真实结论,说明它不只是消除噪音,而是**修正了错误数字** ——
那需要逐条复核白名单。实测**未变**,故修复是**纯粹的稳健性提升**。

### 2.2 顺带发现:动态 `import()` 不被支持

```
注入 const m = await import('../combat/damage.ts');  →  24/50 无变化
```

**与 R6 原实现行为一致**(旧正则同样不匹配 `import(` 形态),故**不是回归**。
记为已知边界。实际影响为零 —— 全仓生产代码无动态 `import()`。

## 三、WS-06:552/553 修复(Lead 批准)

按 alchemy-core 对另 4 处的既有写法改:

```ts
/* 期望值写**字面量 16**,不引 `ICON_SIZE`。
   schema 的 minItems/maxItems **直接取自 ICON_SIZE**(见 prompt.ts 的 pixel_icon_16x16 定义),
   故引用 `ICON_SIZE` 会让两边同步移动 —— 把常量改成任何值这两条都恒真。 */
eq(icon.minItems, 16, 'pixel 数组最小 16 项');
eq(icon.maxItems, 16, 'pixel 数组最大 16 项');
eq(ICON_SIZE, 16, 'ICON_SIZE 本身 = 16(设计基线,像素阵 16×16)');
```

### 3.1 一个重要的技术细节:`eq` 会 `throw`,所以两条断言**串行短路**

第一次验收时 552 变红而 553「没出现」。**这不是 553 仍恒真** ——
查 `shared/testing/harness.ts:162`,`eq` 失败即 `throw`,所以同一 test 内
**552 失败后 553 根本不会执行**。

**若我据此判「553 未修复」,就会报一个假缺陷。** 故做了**交换顺序实验**独立证明 553:

```
交换两行顺序 → 让 maxItems 先执行 → 注入 16→8
  ⇒ pixel 数组最大 16 项  期望 16 / 实际 8   ← **变红,不再是恒真** ✓
  ⇒ (对照)552 此轮未执行(被 553 抢先 throw,符合预期)
```

还原后 WS-06 仍 `61/61`。

### 3.2 三条判据

| 判据 | 结果 |
| :--- | :--- |
| ① 注入 16→8 ⇒ 552/553 **必须变红** | ✓ 552 直接变红;**553 经交换顺序独立证明变红** |
| ② :111/112 **仍然变红**(别改坏有牙齿的) | ✓ 4 条「行数/行宽」相关失败 |
| ③ WS-06 仍 **61 条**(README 不飘) | ✓ |

**「WS-06 仍是 61 条」这点我预判对了**:只换期望值、不加断言,总条数不变。
