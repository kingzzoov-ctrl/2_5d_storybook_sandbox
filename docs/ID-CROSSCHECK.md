## 4. 三处疑点的逐条取证

### 4.1 疑点 A:`boss_ginger_troll` 的 loot 含自己的召唤祭品 739

**手册原文**

- L437(§3.10):「`739` | **【祭品】皇家焦糖彩虹姜饼屋** | Boss召唤 | `焦糖威化木×20 + 高弹果冻胶×10 + 皇家蜂蜜×5` | 放置在甜点奇境祭坛上,召唤 **【甜点Boss:暴食翻糖姜饼巨魔】**」
- L500(§4.3):「**6. 甜点:暴食翻糖姜饼巨魔** …| `8,500 EXP`、**皇家甜点主题全套城堡图纸与姜饼人随从** |」
- L491:「献上表 3.10 中的【召唤祭品】即可唤醒对应群系 Boss」

**代码现值**

- `shared/constants/bosses.ts:94` `summonItem: 739`
- `shared/constants/bosses.ts:96` `loot: [739, 609]`

**判断:真漏洞(经济闭环),且是 8 个 Boss 里唯一一处。**

取证要点:

1. **739 的语义纯粹是祭品。** 它的 `tags` 是 `['Boss召唤','祭品','甜食','甜点']`,手册 L437 明写用途只有「放在祭坛上召唤」。代码里 734~741 这 8 个祭品**不进任何配方**(实测遍历 320 项,引用祭品的配方数 = 0),所以祭品是纯消耗品。
2. **只有这一个 Boss 自反馈。** 扫描全部 8 个 Boss:`loot ∩ summonItem` 只有 `boss_ginger_troll` 命中。其余 7 个都干净。
3. **手册从未说姜饼巨魔掉祭品。** L500 的战利品是「全套城堡图纸与姜饼人随从」,代码里 `城堡图纸`/`姜饼人随从` 两个字符串在 320 项物品表中**都不存在**(未命中)。而 609 是「气球肚皮漂浮饮(恶作剧锅)」,手册战利品列也未提及。
4. **循环确实闭合。** `raid.ts:218` 个人掉落按 `def.loot` 逐项发放,数量 `1 + floor(damageShare×2)`(最少 1)。所以打死一次必得至少 1 个 739 → 可再造祭品 → 可再召唤。**同一份祭品成本可以无限次复用**,且每次还额外产出 609。这不是数值偏高,是**成本归零**。
5. **`summonBoss` 不消耗祭品**(`raid.ts:87~103`):它只校验 `req.itemId !== def.summonItem`(L94),函数内**没有任何扣除调用**;全仓 `consumeItem` 只有定义(`repo.ts:615`)、**无生产调用点**。也就是说「消耗」这一环目前根本没实现 —— 但只要实现,739 自反馈就会立刻变成无限刷宝。

**建议(需 owner 定,不改冻结层):** 把 `loot` 里的 `739` 换成手册真正写的「城堡图纸 / 姜饼人随从」对应的物品 ID(当前 320 项表内无对应条目,需新增或指定替代),或至少删掉 `739`、保留 `609`。同时补上「召唤时扣祭品」这条链路,否则祭品不消耗,任何「掉祭品」都会退化成无限资源。

### 4.2 疑点 B:`boss_beaver_mecha` 的 `loot = [703, 437]`

**手册原文**

- L496(§4.3):「**2. 河谷:机甲河狸·大坝粉碎者** …| `1,600 EXP`、`703 河狸钢牙×10`、**自动伐木机甲宠物图纸** |」

**代码现值**

- `shared/constants/bosses.ts:34` `summonItem: 735`,`:35` `exp: 1600`(EXP **对**),`:36` `loot: [703, 437]`
- `437` = `叮当蒸汽小火车头`(items.ts:265) —— 这是**多人载具**,配方 `寒铁金属锭×6 + 黄铜金属锭×4`,手册 §3.7 L313 定义为「沿轨道高速行驶,撞击铁轨上的野生怪物可直接造成 150 点碾压击飞伤害」。它与「自动伐木机甲宠物图纸」毫无关系。
- 代码里**不存在**「自动伐木机甲宠物图纸」这件物品(全表检索 `自动伐木机甲` 零命中)。
- 另外:**数量 ×10 无处表达**。`BossDef.loot` 的类型是 `number[]`(`entities.ts`),只有 ID 列表,**不含数量字段**;实际数量由 `raid.ts:219` 按伤害份额算出 `1 + floor(share×2)`(1~3 之间)。而手册对野怪掉落是 `Record<number, number>`(带数量),唯独 Boss 战利品丢了数量维度 —— 所以「703 ×10」在数据模型里**根本无法表示**。

**判断:真偏差,两处。**

| 子问题 | 判断 |
| :--- | :--- |
| `437` 是否等于「自动伐木机甲宠物图纸」 | **否**。437 是蒸汽小火车头(载具),语义完全不符;手册所指物品在代码中不存在 |
| `703` 的 ×10 在哪定义 | **没有定义**。`loot: number[]` 缺数量字段,运行时浮动 1~3,与手册「×10」差一个数量级 |

**建议(需 owner 定):** `703` 保留但需补数量维度(把 `loot` 扩成 `Record<number, number>`,或新增 `lootCounts`;这会动冻结层签名,属 CR 级);`437` 应替换。若暂无「机甲宠物图纸」物品,可考虑先只留 `703` 并在文档标注缺口,而不是拿一个载具顶替 —— 那会让玩家拿到与 Boss 主题无关的道具。

### 4.2b 同类问题:`boss_sky_whale` 的 440 与 ×15 也表达不了

同一类偏差在云鲸身上有一组(**手册 L501**):

- 手册:「`12,000 EXP`、`117 极光星辰碎片×15`、`718 极光星辰魔导师杖`」
- 代码:`loot: [117, 718, 440]`(`bosses.ts:111`)
- **`440` 八人云海探险飞艇是手册战利品列里没有的**(手册在破防机制里提到 440 是「驾驶飞艇贴近云鲸」的**手段**,不是掉落物 —— 把攻坚工具当战利品发,语义就串了)

**判断:真偏差 2 处(多给 440、少表达 ×15),与疑点 B 同源。** 这说明「Boss 战利品缺数量维度」不是孤例,而是**系统性缺口**:手册在 Boss loot 上普遍带数量(`703×10`、`117×15`),而 `BossDef.loot: number[]` 天生装不下。

### 4.2c 反向缺口:`boss_chronos_colossus` 少一件

- 手册 **L502**:「`25,000 EXP`、`708 永动发条太阳核`、`723 克洛诺斯磁暴齿轮炮`、**纯金通关纪念碑**」
- 代码:`loot: [708, 723]` —— **少了「纯金通关纪念碑」**(该物品在 320 项表中不存在,与 §5 的抽象产物同类)

**判断:真偏差 1 处**,属「手册有文字、代码无此物品」的缺口(§5 已列)。

### 4.3 疑点 C:配方 #237 / #245 的「任意染料」被硬编码成 #166

**手册原文**

- L178(§3.4):「`237` | **七彩颜料水球** | 涂色/致盲 | `陶瓷空药水瓶×1 + **任意染料**×1` | …」
- L186(§3.4):「`245` | **手持庆典烟花筒** | 氛围/惊吓 | `翠玉青竹×1 + 爆裂火椒×1 + **染料**×1` | …」
- 对照 L185:「`244` | 果冻怪伪装壳 | … | `高弹果冻胶×3 + **翡翠森林染料**×1` |」—— 此处手册**点名了具体染料**(168),说明手册作者是刻意区分「任意」与「指定」的,不是随手写的。

**代码现值**

- `items.ts:130` `237` → `recipe: { 165: 1, 166: 1 }`
- `items.ts:138` `245` → `recipe: { 103: 1, 126: 1, 166: 1 }`
- `items.ts:137` `244` → `recipe: { 162: 3, 168: 1 }`(**正确**,按手册点名 168)

**判断:是错误,但属「数据模型缺表达力」导致的降级,不是随手写错。**

取证与可行性:

1. **数据模型不支持。** `ItemDef.recipe?: Record<number, number>`(`entities.ts`)—— 键只能是**具体数字 ID**,没有 tag、没有 `any` 通配、没有 `oneOf`。所以「任意染料」在当前结构下**无法表达**,实现者只能挑一个 ID 顶上,于是挑了 166(绯红,四色中的第一色)。
2. **后果是实打实的**:玩家手握 167/168/169 三种染料时,制作 237/245 **会失败**。而染色/涂色玩法本身就鼓励集齐四色,这让另外三种染料在这两个配方上变成废料。
3. **染料确实是「同类」的**:166~169 四件物品的 `tags` 全部含有 `"染料"`(166/167/168 为 `['染料','颜料','容器']`,169 为 `['染料','发光','颜料']`)。所以**用 tag 匹配在语义上是成立的**。
4. **仓库里已有 tag 匹配的先例**,但**不在配方系统里**:`server/src/alchemy/degrade.ts` 的 `SilhouetteRule` 用 `anyTags: readonly string[]` + `rule.anyTags.some((t) => set.has(t))`(L102)做「任一 tag 命中」判定。这是现成的实现范式,可移植。

**可行的两种做法(都不必现在动手,需 owner 裁决):**

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| A. 扩 tag 配方 | `ItemDef` 增 `recipeAnyTag?: Record<string, number>`,如 `{ '染料': 1 }`;合成校验时对每个 tag 要求「背包内该 tag 物品总数 ≥ 需求数」 | 改冻结层类型;需同步 `blueprint.ts:315`(递归展开配方)、`data-conformance.ts` 与校验脚本;试算成本公式要按最低价 or 最高价染料计价,需定规则 |
| B. 显式多配方 | 把 237 拆成 4 条配方(166/167/168/169 各一条),合成表按「任一命中即可」匹配 | 不动类型,但配方表结构与「一 ID 一配方」的现状冲突,需改合成入口匹配逻辑 |

方案 A 更贴近手册语义;方案 B 改动小但会让「一物品多配方」成为新常态。**两者都要动冻结层或合成引擎,超出本次核查范围,故此处只给可行性,不落实现。**

## 6. 结论汇总

| 核查项 | 差异条数 | 结论 |
| :--- | ---: | :--- |
| 320 项物品(§3.1~§3.10) | **0** | 分节数量与 ID 上界全对齐 |
| 24 生物 ID / 名称 | **0** | 手册与代码逐字一致;等级/HP/EXP 亦全一致 |
| 24 生物掉落 | **4** | 1 一致(capybara 建模正确)、3 近似顶替(见 §5) |
| 8 Boss 名称 | **1** | 克洛诺斯:手册 L502 与 L439 自相矛盾,代码随 L439 |
| 8 Boss 等级/HP/EXP | **0** | 全一致 |
| 8 Boss 战利品 | **7**(涉及 4 个 Boss) | 739 自反馈(真漏洞)、437 错替、440 越界、少了纪念碑;另 `703×10` 与 `117×15` 是 `loot` 缺数量维度的系统性缺口 |
| 237/245「任意染料」 | **2** | 硬编码 166,另三种染料在这两配方上失效 |

| 设计稿 vs 代码(生物 ID) | **15** | 设计稿用缩写 ID,手册/代码用完整 ID,以手册为准 |

**三个疑点的定性:全部成立,无一是误报。**

- A(739 自反馈):真漏洞,影响经济闭环,8 Boss 中唯一。
- B(437 + ×10):真偏差,两处独立问题,其中「×10」暴露 `loot` 类型缺数量维度。
- C(任意染料):真降级,根因是 `recipe` 类型无法表达 tag,仓库内已有 tag 匹配范式可移植。

**额外发现(超出三个疑点,因同源而记录):** Boss 战利品共 7 处偏差,集中在 4 个 Boss

| Boss | 手册战利品(L495~L502) | 代码 `loot` | 问题 |

| `boss_fox_kitsune` | 705、720 | `[705,720]` | 一致 |

| `boss_ginger_troll` | 城堡图纸、姜饼人随从 | `[739,609]` | **739 自反馈漏洞**;两项手册物均无 ID |

**4 个 Boss 干净,4 个有问题。** 规律很清楚:凡手册给了数量(`×10`/`×15`)或给了「没有 ID 的抽象奖励」(图纸/随从/纪念碑),代码就会出偏差 —— 因为 `loot: number[]` 既装不下数量,也装不下抽象物。**根因是同一个数据模型限制**,建议一并作为 CR 处理,而不是逐条打补丁。

三处都涉及 **`shared/**` 冻结层**(`bosses.ts` 的 `loot`、`entities.ts` 的 `loot` 与 `recipe` 类型),本次核查**未做任何修改**,是否开 CR 由 Lead 决定。
