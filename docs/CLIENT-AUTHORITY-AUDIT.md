# 客户端本地权威点审计(task-67 阶段 1)

> **任务**:task-67 阶段 1 · **作者**:`client-stage`(WS-09 2.5D 舞台渲染与客户端 UI)
> **性质**:★ **只读审计** —— 未修改 `client/**` 任何一行。本文只输出清单。
> **动机**:`docs/CLIENT-NET-GAP.md` 已证「客户端联机层缺失」是**计划层的洞**;
> 而在写任何网络代码**之前**,必须先知道**哪些本地状态会被网络接管** ——
> 否则会出现「网络值与本地值同时写同一个显示」的分叉,而**任何门禁都看不见**。
>
> **标注约定**:「**实测**」= 实跑探针,附命令;「**读码**」= 静态读源码;「**未实测**」= 未验证。
> **前作**:`docs/CLIENT-NET-GAP.md`(25,223 B)、`docs/CLIENT-NET-READINESS.md`(21,703 B)、`client/src/net/prediction.ts`(457 行)。

## 0. 一句话结论

**客户端不是「有一个网络层的小缺口」,而是「整个运行时复杂度都建在『本地即权威』这个假设上」。**
本审计在 `client/**`(24 个 `.ts` / 9,649 行 + `index.html`)里找到 **14 类本地权威点**,
其中 **2 类会静默分叉**(接入网络后行为改变但**不报错、断言不红**)——
正是任务书点名的那两处。**其余 12 类可以当场判定为「接入后无歧义」,已在 §2 分类说明。**

**⇒ 最关键的一条**:`pan`(相机)与 `playerGx/playerGy`(玩家格)是**同一个值**。
现在两者**恰好相等**,所以「用相机位置当玩家位置」这个错误**不可观测**。

## 1. ★★ 两个静默分叉点(优先修)

### A1 `pan` 与 `playerGx/playerGy`:相机空间 ≡ 世界空间

| 项 | 内容 |
| :--- | :--- |
| **位置** | 声明 `client/src/three/boot.ts:710` `const pan = { x: WORLD_CELLS/2, y: WORLD_CELLS/2 }`;别名声明 `:552-553`;★ **无条件赋值在 `:1033-1034`**(`tick()` 内) |
| **它现在从哪来** | **本地键盘输入**。`:1018-1021` 读 `keys` Set → `:1024-1025` `pan.x += (dx/len)*speed`,`speed = 12*dt/1000`(`:1015`)。也来自 URL 钩子 `?at=gx,gy`(`:786-787`)与 `__uiDebug.teleport()`(`:744`) |
| **接入网络后应从哪来** | `pan` 应**只由相机逻辑**控制(可保留本地自由视角);`playerGx/playerGy` 应来自**服务端快照**的玩家坐标(经 `prediction.ts` 的 `reconcile`/`Interpolator`) |
| **★ 现在为什么不报错** | **两者被同一个表达式绑定,恒等**:`boot.ts:1033 playerGx = pan.x;`(`:1034` 同理)。`playerGx` 只喂 **1 个消费者**(`:568` 屋顶判定;另 `:821-822` 喂预警圈圆心),而该消费者对「玩家在哪」的**期望恰好等于「相机看哪」**——因为 demo 里没有独立的玩家实体。**⇒ 等式成立时,「用相机位置当玩家位置」与「用玩家位置」不可区分。** |
| **接入网络后的表现** | 相机继续被 WASD 推(本地),玩家坐标改由服务端下发 ⇒ `playerGx ≠ pan.x`。**但 `:1033-1034` 那两行赋值仍在**,会把服务端的值**立刻覆盖回相机值** ⇒ 屋顶仍按**相机**位置淡出。**表现:走到屋顶下不淡出 / 在空地上淡出。不报错、断言不红。** |
| **实测证据** | 见 §5 的 P1/P2/P3 |

> ⚠️ **`:1033-1034` 是这个缺陷的载体**。它不是「少了一行」,而是「**多了一行无条件覆盖**」。
> 接入网络时如果只加「从服务端读 playerGx」,这两行会把它**静默抹掉**。

### A2 `bossHp`:Boss 血量由客户端按时间递减

| 项 | 内容 |
| :--- | :--- |
| **位置** | 初值 `client/src/three/boot.ts:490` `let bossHp = boss ? boss.baseHp : 0`;★ **递减在 `:1041`**;重置 `:937` |
| **它现在从哪来** | **冻结层常量 + 本地时间积分**。`:489` `const boss = BOSS_LIST[0] ?? null`(★ **不来自服务端状态**),`:1041` `bossHp = Math.max(boss.baseHp*0.18, bossHp - (dt/1000)*boss.baseHp*0.035)` |
| **接入网络后应从哪来** | 服务端 `BossState.hp`(见 `server/src/net/schema.ts` 的 Boss 实体表) |
| **★ 现在为什么不报错** | 客户端**没有任何「Boss 血量」的对照物** —— 服务端状态从不下发到 client(实测:client 全仓 0 处网络痕迹),所以「本地算的」与「服务端算的」不可能被比较。**断言只检查「血条在下降」(方向),不检查「下降对不对」(数值)**。 |
| **接入网络后的表现** | 服务端下发 `hp`,而 `:1041` 每帧继续本地递减 ⇒ 两个写者**同时**写 `bossHp`。表现为**血条掉得比真实快**(本地衰减与服务端值叠加/互相覆盖),且**根因在客户端,服务端侧一切正常**。 |
| **附:`bossGhost` 是同类** | `:491` `let bossGhost = 1`,`:1040` `bossGhost = Math.max(bossHp/boss.baseHp, bossGhost - (dt/1000)*0.06)`。它是**纯本地视觉残影**(UI 平滑量),接入网络后**可以保留本地**——已按 §3 的判据单独归类,见 B 类。 |

## 3. ★ 一个重大发现:客户端「背包」没有「拥有」这个概念

**这是我在扫 F3 时发现的,不在任务书的清单里。**

```ts
// client/src/ui/inventory.ts:345-359  filterItems()
for (let i = 0; i < ITEM_LIST.length; i += 1) {     // ← 遍历**全部 320 件**配表物品
  const item = ITEM_LIST[i];
  const ok = (!cat || item.category === cat) && matchesQuery(item, q) && ...;
  if (!ok) continue;
  out.push({ slot: i, row: ..., col: ..., item, visible: true });
}
```

**实测**:`filterItems({})` 返回 **320** 件,`TOTAL_ITEM_COUNT` = **320** ⇒ **完全相等**。

```
inventory.ts 里这些词的出现次数:
  "stock" / "have" / "amount" / "owned" / "carried"  ⇒ **全部 0 次**
```

**⇒ 客户端所谓的「背包视图」是「配表浏览器」,不是「玩家持有物」。**
`boot.ts:457` 的 `RECIPE_STOCK`(硬编码 `Map([[101,8],[102,4],[103,2]])`)是**唯一**的「持有量」概念,
而它只喂配方树的 `checkCraft`,**与背包面板完全不通**。

**接入网络的后果**:服务端有权威背包(`room.ts:663 applyInventory` + `db` 的 `inventory_json`),
但客户端**没有任何字段能承接它** —— 这不是「接线」,是「**先要有这个概念**」。
⇒ **建议**:把「持有量」作为 `InventoryView` 的一个新输入(而非重写 `inventory.ts`)。

**⇒ 未实测**:我没有验证「服务端也确实认为玩家拥有全部 320 件」
(那需要读 `server/src/**`,不属本任务写域,也未在本轮扫描面内)。
