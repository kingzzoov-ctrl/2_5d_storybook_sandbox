## 二、生产可达性:两个模块确证「只被测试 import」

这是本轮最重的结构发现。用 `grep` 遍历 `server/src` + `client/src` + `shared` 的**全部 import 语句**:

### 2.1 `server/src/combat/damage.ts` —— 零生产调用方

```
严格匹配 import 语句中的 damage 模块:  (无输出)
生产目录 importer:                       无
唯一的引用者:                            tests/WS-10.test.ts:21
```

`world_sim.ts` 走的是**另一条**路径:只 import `combat/vitals.ts`,不 import `damage.ts`。
项目自己的 `docs/FOUNDATION-AUDIT.md` §3.6 已记录此事(「combat/ 下 5 个模块,合计约 2300 行,只被测试 import」),
**我的独立复核与它一致**。

- **后果**:玩家打生物的八步公式(暴击/闪避/元素/格挡/击退/吸血/破盾)在生产中不可达;
  `damage.ts` 算出的 `knockbackImpulse` 生产内零消费者。
- **但**:这不等于「WS-10 的断言是装饰」。断言的**区分力**是真实的(见 §3.1),
  缺的是**生产接线**。两者必须分开裁决 —— 混为一谈会得出「测试没用」的错误结论。

### 2.2 `server/src/wiring/components.ts` —— 零生产调用方(确证 Lead 判断)

```
谁 import 了 wiring/components.ts?(生产目录)  → 零命中
对照:graph.ts 有生产 importer → build/wiring_view.ts, sim/world_sim.ts, wiring/components.ts
world_sim 调用 components 的任何函数:        false
world_sim 有 wiring.tick() 调用:              true
world_sim 有 drive():                         true
```

**Lead 的「40 项电路件全是空壳」判断成立**:`world_sim` 只驱动**线**(`SignalGraph`),
从不调用任何**件**的求值函数(`createComponent` / `counterStep` / `channelMatches` / `relayTicksFor` / `chooseSplitterRoute` 全部零调用)。

### 2.3 集成层对电路的检查只有一条,且极弱

```
verify.ts:726:  ['电路通电格', snap.wireCells > 0, '期望 > 0(布线且已驱动),实际 ...']
verify.ts 含 components.ts:  false

verify.ts 含 channelMatches: false
verify.ts 含 relayTicksFor:  false
```

**集成层只验证「线能通电」,从不验证「件能求值」。**
把 `components.ts` 整个删掉,只要线还能亮,集成门禁依然是绿的。

> 这与 `FOUNDATION-AUDIT.md` §3.7 的建议完全一致(「建议把自检改为『铺一条线 + 放一个 SENSOR_LEVER + 断言其 state 发生变化』」)。

#### 3.1.1 真实假绿:`REFLECT_RADIUS` 断言是同义反复

**最小复现**(3 步):

```
1) 改 server/src/combat/damage.ts:39
   export const REFLECT_RADIUS = 3.0;   →   export const REFLECT_RADIUS = 999;

2) node tests/WS-10.test.ts

3) 观察:[WS-10] 44/44 通过   ← 全绿
```

**根因**(`tests/WS-10.test.ts:319`):

```ts
eq(sep.radius, REFLECT_RADIUS, '反伤作用半径 3 格');
```

右侧判据 `REFLECT_RADIUS` 是**被测模块自己的导出常量**。实现改多少,判据就跟着改多少,
等式恒成立 —— 这条断言**在数学上无法失败**。它测的是「`sep.radius` 是否等于它自己被赋的那个值」,
而不是「半径是否等于手册的 3 格」。

**修法**:把右侧换成立字面量 `3.0`(或取自冻结层的独立值),与同一文件里 204 处健康断言的写法保持一致。

#### 3.1.2 但多数「同义反复嫌疑」是误报

我扫出 20 处形如 `eq(x, <被测模块导出常量>)` 的断言。逐条看,**绝大多数是枚举值比对**:

```ts
eq(ally.source, DamageSource.PRANK);        // 枚举 —— 合法
eq(s723.shape, SkillShape.AREA);            // 枚举 —— 合法
eq(outcome.result!.method, ReviveMethod.TOUCH);  // 枚举 —— 合法
```

枚举比对不是同义反复:枚举成员本身就是**语义定义**,断言「走的是这个分支」是有效的信息。
真正危险的是**数值型**同义反复 —— 本批只发现 `REFLECT_RADIUS` **一处**。

> 这也说明扫描器给出的「20 处嫌疑」不能直接当 20 个缺陷报,**必须逐条人工定性**。
> 我在第 1 批也踩过同类坑(`rowAligned` 误判为恒真),故此处格外保守。

## 10. R6 已实施:生产可达性门禁

R6 已由 Lead 授权实施,落在 `scripts/verify.ts` 的 `checkReachability()`,每次 `verify` 都会跑。

### 10.1 为什么这条门禁值得做

本仓反复出现的缺陷类是「**完整实现、单测全绿、编排层不接**」。
这类缺陷的共同特征:**不会让任何测试变红**,因为它压根不在生产路径上。
本批两个模块(`combat/damage.ts` 约 2300 行、`wiring/components.ts` 40 项件)
都是靠人工 grep 才发现的 —— 没有门禁,下一次仍要靠运气。

### 10.2 口径

| 项 | 值 |
| :--- | :--- |
| 生产入口 | `server/src/sim/demo.ts`(`npm run sim`)、`server/src/net/room.colyseus.ts` |
| 扫描范围 | `server/src/**` + `client/src/**` |
| 模块总数 | **74** |
| 可达 | **23** |
| 不可达 | **51**(全部在白名单内,附理由) |
| 闭包算法可靠性 | 全仓 191 条相对 import **0 条解析失败** |

> 入口只认**真的会启动服务/模拟**的文件。工具脚本(`scripts/**`)不计入 ——
> 把它们算作根会让几乎所有模块都「可达」,门禁随即失去意义。

### 10.3 设计要点:警告 + 可断言数字 + 升级开关

**为什么默认是警告而非 fail**:不可达有合理情形(本仓无客户端装配入口,
`client/src/**` 16 个模块必然不可达)。一上来 fail 会被立刻加白名单绕过,反而失去意义。
所以**先让它可见,再逐步收紧**。

**但它不能是装饰** —— 这有两层保障:

1. **数字可断言**:输出 `可达 23 / 不可达 51 (共 74,入口 2 个,白名单 51 条)`。
   任何一条数字变化都可被察觉,而不是「一条永不失败的绿色通行证」。
2. **`--strict-reach` 开关**:把「未登记的不可达模块」从告警**升级为失败**。
   若只有告警,「永远是警告」本身又会退化成装饰。

### 10.4 白名单自检(与 `DECORATOR_EXEMPT` 同一思路)

白名单每条必须**写明理由(≥8 字)**,且自检四类失真:

| 失真类型 | 检测 |
| :--- | :--- |
| 文件不存在(改名/删除) | ✓ 报「文件不存在」 |
| 理由缺失或过短 | ✓ 报「未写明理由」 |
| **已变成可达**(过时条目) | ✓ 报「已可达,应移出白名单」 |
| 生产入口本身不存在 | ✓ 报「门禁口径失效」 |

### 10.5 故障注入(5 项,全部生效)

| # | 注入 | 观察 | 结果 |
| :--- | :--- | :--- | :--- |
| A | 新建无人 import 的 `server/src/world/_orphan_probe.ts` | 不可达 **51 → 52**,并报出模块名 | ✓ 数字变化 + 告警 |
| A' | 同上 + `--strict-reach` | `✗ 新增未登记的不可达模块 1 个` → 退出码 1 | ✓ 升级路径有效 |
| B | 白名单登记不存在的路径 | `✗ 白名单失真:…(文件不存在)` | ✓ |
| C | 白名单条目理由写成 `'x'` | `✗ 白名单失真:…(未写明理由)` | ✓ |
| D | 把**已可达**的 `world/grid.ts` 放进白名单 | `✗ 白名单失真:…(已可达,应移出白名单)` | ✓ |
| E | 把生产入口改成不存在的路径 | `✗ 生产入口不存在(门禁口径失效)` | ✓ |

A 注入删除后恢复 `可达 23 / 不可达 51`,数字归位。

### 10.6 附加发现

手工核这一项时又抓到 2 处此前从未被点名的不可达模块:

- **`server/src/net/prediction.ts`** —— WS-07 客户端预测,生产目录**零命中**(已核实)
- **`server/src/db/driver.sqlite.ts` / `memory_db.ts`** —— 全仓唯一 importer 是
  `tests/WS-07.test.ts`;生产侧只以 `DbLike` 结构化类型接收,从未注入具体驱动

后者是本门禁的一个**已知边界**:它只跟踪静态 `import` / `from`。
`repo.ts` 的注释写着「真实 SQLite 绑定由 `driver.sqlite.ts` 通过结构化类型注入」——
听起来像动态加载,但**实际全仓没有任何 `import()`**,
两个驱动只被测试 import。所以这不是「刻意不静态接」,而是**生产侧真的没接**。

> 这个区别很关键:白名单理由必须区分「暂不接」与「刻意不静态接」。
> 我最初把它写成「由 `repo.ts` 按需加载」——**这是错的**,核实后已改正为「尚未注入」。
> 若不核实就写理由,白名单本身就会变成掩盖真实缺口的工具。
