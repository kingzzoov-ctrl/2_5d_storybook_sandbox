## 1 起源:一个被推翻的假设(附完整证据)

### 1.1 我(以及任务书)原本的判据 —— 错的

`task-62` 的任务书给了一个三分类,其中一类是:

```
乙 值来自「与断言同一表达式」  例:eq(f(x), g(x)) 而 f/g 同源;或 eq(x, x)
   ⇒ **恒真,改什么都没用** —— 这类是无声的,永远绿
```

按此判据,我的审计脚本报出 **25 条乙类**,并准备把它们当作「没牙的断言」清单交上去。

### 1.2 决定性实验:它其实守得住一个真实缺陷类

挑 `tests/WS-FND-02.test.ts:401`(属于测试 `A21 同输入序列必产出同投递序列(无 Math.random)`):

```ts
const run = (): string => {
  const b = new EventBus();
  const got: string[] = [];
  b.on('*', (e) => got.push(`${e.kind}@${e.frame}`));
  for (const k of ['a', 'b', 'c', 'a', 'b']) b.emit(k);
  b.drain();
  for (const k of ['d', 'a']) b.emit(k);
  b.drain();
  return got.join('|');
};
eq(run(), run(), '两次完全一致');       // ← 两侧文本完全相同
```

**注入:把 `EventBus` 产生的事件帧号改成真非确定性**

```diff
  // server/src/events/bus.ts:236
- const e: GameEvent = { kind, payload, source, frame: this.frameCount };
+ const e: GameEvent = { kind, payload, source, frame: Math.floor(Math.random() * 1e9) + this.frameCount };
```

**实测输出**:

```
目标测试「A21 同输入序列必产出同投递序列」:**红**
套件通过数:65/65 → 63/65
新红:A21 同输入序列必产出同投递序列(无 Math.random)
      C02b 事件在**当帧**投递,不留到下一帧
```

### 1.3 结论:**语法形态 ≠ 语义性质**

```
Lead 的判据(以及我照抄的那份)把「同义反复」当成一个**语法形态**(两侧同源),
而它其实是一个**语义性质**(改哪个输入都不会红)。

两者不是一对一:
  eq(run(), run())  —— 两侧**写法**同源,但**语义上不同源**
                       (run 内部有非确定性 ⇒ 两次调用返回的不是同一个值)
⇒ 「两侧写作同源」是**语法**;「改什么都不红」是**语义**。
  语法形态只能**提示**语义性质,不能**决定**它。
```

**⇒ 处置:这 25 条一律不动。** 若要动任何一条,必须配一个「注入到它声称守的那个缺陷类」的实验。

## 2 核心方法:判据有牙性实验(三步)

**适用对象**:任何「声称守某个东西」的判据 —— 断言、门禁检查、审计脚本的检测器。

### 第 1 步 · 问:它声称守什么缺陷?

**必须从判据本身读出这个答案,不能从它的名字读。**

```ts
test('面板布局:格子尺寸自洽(格子数 × 格宽 = 网格宽)', () => {
  eq(L.cols * L.rows, L.cols * L.rows, '网格格数 = 列×行');
  ...
```
- 名字声称:**格子数 × 格宽 = 网格宽**
- 实际断言:`eq(X, X)` 其中 `X = L.cols * L.rows`(甚至不是标题说的那个量)

⚠️ **名字与内容是两件事**。本仓已有先例:测试名写着「无 Math.random」,而那条
`eq(run(), run())` 并不是靠名字守它的 —— 是靠**被测实现真的注入 rng** 才守住的。
**名字只是线索,断言体与被测算才是判据。**

### 第 2 步 · 注入:构造那个缺陷的**最小实例**

判据有两类,**必须区分**,因为它们的注入方式不同:

| 判据在守 | 注入什么 | 例 |
| :--- | :--- | :--- |
| **值正确性** | 改上游/权威,让正确值变成错的 | `MAX_MOVE_CATCHUP_TICKS 1→2` |
| **性质**(确定性/不变量/单调性) | 让实现**违反该性质**,但不必让它错 | 给确定性被测函数注入 `Math.random()` |

⚠️ **第二类是本仓最容易漏的**。`eq(run(), run())` 守的是**性质**,不是值。
注入「改个常量」对它毫无影响 —— 必须注入**性质的违反**。

### 第 3 步 · 三态判定,不许二值

```
有牙    注入该缺陷 ⇒ 判据变红             ✅ 可信
没牙    注入该缺陷 ⇒ 判据仍绿             ⚠️ 但先做第 4 步
无法判定  ℹ️ **本方法在结构上不适用**(见 §5)
```

⚠️ **不允许把「无法判定」写成「没牙」**。这是本仓 `assertion-audit.ts` 12 个检测器
的同一纪律:启发式判定的诚实做法是把边界显式标出来。

## 3 ★ 第 4 步(必做):反向核查 —— 因为「没牙」这个结论**天然可疑**

**这是本文最重要的一节。**

当实验返回「没牙」时,你得到的是**你想要的结论**。这时**必须先查反向**。

### 3.1 四种形态(前三种已有记录,第四种是 `task-65` 新增)

```
31-1  「一条注入没红」      ⇒ 可能是注入没生效
31-2  「阴性对照绿」        ⇒ 可能是对照选错了
31-3  「探针坏了却伪装成支持你的假设」
31-4  ★「**扫描范围缺失 ⇒ 输出恰好符合期望 ⇒ 不查就交卷**」
```

**31-4 比前三种更危险**:

```
前三种都有「红或不红」这个**摩擦** —— 你会停下来看。
第 4 种是**静默地**给你想要的答案,**没有任何摩擦**。
⇒ 唯一防线是「**这个结果太符合我的假设了 ⇒ 去查反向**」这个直觉。
⇒ 而它**不可自动化**。它不能做成门禁、不能写成检测器。
   它是人的一次主动怀疑行为。
```

### 3.3 反向核查的标准动作(可照抄)

```
① 验证「判红器」本身能看见红
   做法:注入一个**已知必红**的东西,确认目标 test 真的变红
   实例:注入 `CELL_INSET = 99999` ⇒ 目标 test 红了(103/104)
        ⇒ 判红器有效 ⇒ 后面的「绿」才是信息

② 验证「注入真的改变了被观测的值」(≠ 文件变了)
   ⚠️ 这两件事不同!见 §4 的注入 C:
      改的是 `gridX + col*cell + 3`,而断言测的是 `r1.x - r0.x`
      ⇒ (gridX + cell + 3) - (gridX + 0 + 3) = cell  ← **+3 被减掉了**
      ⇒ 文件变了,被观测的值没变 ⇒ 注入**数学上惰性**
   ⇒ 动作:跑一个**独立最小复现**,打印注入前后的值,肉眼比对

③ 查「结论成立的适用范围」
   动作:grep 一遍「这个量还有谁在读」
   实例:注入 A 破坏 `gridW` 后我 grep 它,发现 gridW 只出现在**返回值构造**里
```

## 4 实例 1:「邻牙掩护」(本文新发现的机制)

### 4.1 事实

```ts
// tests/WS-09.test.ts:3719
test('面板布局:格子尺寸自洽(格子数 × 格宽 = 网格宽)', () => {
  const L = layoutInventoryPanel(VW, VH);
  eq(L.cols * L.rows, L.cols * L.rows, '网格格数 = 列×行');   // ← 3721 **两侧同一表达式**
  ok(CELL_INSET * 2 < L.cell, ...);                          // ← 3723 有牙
  const r0 = slotRect(L, 0);
  const r1 = slotRect(L, 1);
  eq(r1.x - r0.x, L.cell, '相邻格水平间距 = 格宽');            // ← 3726 有牙
  const rRow = slotRect(L, L.cols);
  eq(rRow.y - r0.y, L.cell, '相邻行垂直间距 = 格高');          // ← 3728 有牙
});
```

**标题声称守「格子数 × 格宽 = 网格宽」**,而 3721 断言的是 `cols * rows`(格数),
**且两侧同一表达式**。真正该守的那个量是 `gridW`,它在**全仓断言里 0 次出现**。

### 4.2 实验(注入 A)

```diff
  // client/src/ui/panel_layout.ts:107
- const gridW = cols * cell;
+ const gridW = cols * cell + 7;      // 直接破坏「格子数 × 格宽 = 网格宽」
```

**实测**:

```
=== 注入 C'(对照组:必须有牙)===
  x: layout.gridX + col * (layout.cell + 3)
  ⇒ 目标 test:**红**   套件 104 → 102/104
  ⇒ 对照结论:✓ **本实验能测出红**(判据有效,三次绿不是判红器坏)

=== 注入 A(破坏标题声称的不变量)===
  const gridW = cols * cell + 7
  ⇒ 目标 test:**绿**   套件 104/104
  ⇒ 新红:无

=== 完整门禁(17 套件 · 四旗)===
  基线 exit=0
  注入 A 后 exit=0        ← **零反应**
  全部通过 · 9087ms

=== 还原 ===
  ✓ 逐字节一致
```

### 4.3 结论与机制

```
注入 A 破坏的正是那个 test 标题**自己声称**要守的不变量,
而:
  · 该 test 本身:绿
  · 完整门禁(17 套件 / 四旗):exit 0
```

**先补齐一件事(避免我把话说过头)**:§4.4/§9 里我说「该 test 另有 3 条有牙断言」,
其中 3723 / 3726 由注入直接证明,而 **3728 我起初是由 3726 类比推得的**。
按本仓纪律补验:

```
注入:slotRect 的 y 轴 `row * cell` → `row * (cell + 5)`
  ⇒ 目标 test **红**   套件 104 → 102/104
  ⇒ 3728(垂直间距)**确有牙**   还原 SHA-256 一致 ✓
```
**⇒ 三条(3723 / 3726 / 3728)全部实测有牙,不是推断。**

**⇒ 机制:有牙的断言会给没牙的断言当掩护。**

```
一个 test 只要**有一条**能红的断言,整个 test 就算「通过了」。
⇒ 里面挂多少条恒真断言都不会被发现。
⇒ WS-09 那个 test 里 3723 / 3726 / 3728 三条**实测**都有牙
  ⇒ 只要它们是绿的,test 就绿;
    3721 永远绿这件事**没有任何机会暴露**。
```

**⇒ 这是「如何漏掉没牙断言」的主要机制**,比单条恒真更隐蔽。

### 4.4 为什么现有工具都看不见它

```
· assert(两侧同源)      ⇒ 能看见 3721,但**会把它报成"没牙"**
                            ⇒ 而本文 §1 已证:两侧同源 ≠ 没牙 —— **假阳性**
· judgement_audit.ts    ⇒ 扫门禁脚本的**提取口径**,不扫断言的有牙性
· 门禁四旗              ⇒ 只看「有没有红」,掩护之下什么都看不见
· 覆盖率工具(若有)      ⇒ 看「这行代码被执行了吗」——
                            3721 **每跑必执行**,它是执行得最勤的一行
```

**⇒ 三个维度(语法、执行、结果)全部看不见语义上的「什么都没守」。**

### 4.5 我这一轮的两个自误(必须一并记下,否则上面的结论是我运气好)

```
① 注入 C 数学上惰性(第一版)
   我改 `gridX + col*cell + 3`,而断言测 `r1.x - r0.x`
   ⇒ +3 被减掉 ⇒ **文件变了、被观测的值没变** ⇒ 三次全绿
   ⇒ 若我不加对照组、不查反向,我会得出「WS-09 对该文件完全无区分力」——
     这个结论**过度**了(实际只有 3721 那一条无区分力,另三条有)

② 第一版三个注入全绿,连对照组也绿 —— 这个结果**太漂亮**
   ⇒ 触发 §3.3 的反向核查 ⇒ 才查出 ①
```

## 6 实例 3:门禁脚本的判据(build-wiring 的 C 检测器)

`scripts/judgement_audit.ts` 的 C 检测器(=「import 探测只认 `from`」),

```

        ⇒ 要找的正是**别人写的正则字面量**,而它自己也被剥掉了
        ⇒ 检测器报 0 条 ⇒ 看起来「全仓干净」
⇒ 修法(它自己记的):先把源码里所有反斜杠**去掉**做规范化,
  再做纯字面量 `includes()` 判断 —— 不再有任何转义层。

版本 2  加自检时,脏样本 0 条命中
        ⇒ 是区分力自检当场抓住的

版本 3  正则字面量结尾「转义斜杠 + 收尾斜杠」拼起来正好是两个斜杠
        ⇒ 被自己的剥注释器当成**行注释起点** ⇒ 该行起全部屏蔽
```

**⇒ 它给出的可复用判据**:

```
一个检测器必须:
  在「合成的脏样本」上**报出命中**   ← 否则它是个空壳
  在「合成的干净样本」上**不报**      ← 否则它制造噪音
两者都通过,才算这个检测器成立。
```

**⚠️ 这与本文是同族但不同层**:它守的是「检测器的**提取口径**够不够宽」,
本文守的是「判据**声称守的那个缺陷**真能让它红吗」。**两个问题都问,才完整。**

## 8 失效边界:本方法**做不到**什么

**这一节比前面所有节都重要。** 凡报「没牙」者,必须同时报它的适用边界(陷阱 39)。

### 8.1 结构上做不到的(不是「还没做」,是「这个工具原理上做不了」)

```
① **「两个来源是否真独立」需要跨文件数据流分析**
   task-62 的丙类(两侧独立权威)只报出 8 条,而**实际远多于此**。
   ⇒ 8 是**下界**,不是总数。
   ⇒ 想判 `eq(库值, 运行时权威值)` 是否真独立,必须知道这两个值
     **从哪里来**——那要跨文件、跨函数追数据流。本仓没有这个能力。

② **「某个缺陷类是否可注入」本身是未决问题**
   §4 的注入 A 能生效,是因为 `gridW` 是纯函数、可直接改。
   若一个不变量横跨网络协议 + 序列化 + 反序列化,
   「破坏它」的最小实例**可能不存在**。
   ⇒ 这时只能报「无法判定」,不能猜。

③ **注入的粒度盲区**
   §4 我第一版的注入 C 数学上惰性 —— 我改的是 `+3`,被减掉了。
   ⇒ 「注入没生效」与「判据没牙」的输出**完全相同**。
   ⇒ 只能靠 §3.3-b(跑独立最小复现打印值)分开,**不能靠看**。
```

### 8.2 不可自动化:本文最该记住的一句

```
**「这个结果太符合我的假设了 ⇒ 去查反向」这个直觉,不可自动化。**

它做不成门禁(它要求的是「在结果正确时仍然怀疑」),
写不成检测器(检测器的输入是文本,而它要检测的是**人的确信程度**)。
⇒ 它是 §3.3 那一串动作的**触发器**,而那些动作才是可执行的。
   **触发器本身只能靠纪律。**
⇒ 本仓已有的自动化只能覆盖到 §3.3-a(判红器自检)那一层:
   `judgement_audit.ts` 的 12 个区分力自检、`assertion-audit.ts` 的 12 个检测器自检
   —— 它们能挡住「空壳检测器」,**挡不住「扫描范围缺失」**。
```

### 8.3 已知会让本文方法给错答案的情形

```
· **同一 test 里的邻牙掩护**:§4 已证 —— 只要 test 里有任意一条有牙的断言,
  整个 test 就是「绿的」,里面藏多少恒真都测不出来
  ⇒ 若把「test 红不红」当判据,工具会被掩护骗过
  ⇒ 必须**按断言定位**(本仓无此基础设施,故 §4 我只能手工确认)

· **非确定性被测函数**:同一注入跑两次可能一次红一次不红
  ⇒ 必须固定 rng 种子(本仓惯例:`rng: () => 0.5`)
  ⇒ 我 §1 那个实验里,被测算**有**非确定性,而注入的是「额外的非确定性」
    —— 这**恰好**成立,但不是所有性质类都能这样构造

· **注入影响面过宽**:改一个共享常量会连带打红一堆无关断言
  ⇒ 那时「目标红了」不能证明「目标有牙」(可能是被别处的红牵连)
  ⇒ 必须**按测试名/断言定位判红**,不能按套件通过数
    (task-62 我第一版就是这么错的:6/9「不符」全是测量伪影)
```
