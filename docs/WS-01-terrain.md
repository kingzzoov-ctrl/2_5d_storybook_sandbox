## 1. 职责边界

**本子系统负责**

- 32-bit 单元格的读写、位压缩、五层垂直数据栈的统一访问;
- 16×16 分片(`Chunk`)的生命周期:构造、脏位标记、1KB 序列化、反序列化、快照回滚;
- 分片容器 `WorldGrid`:延迟创建、跨分片坐标归一化、只读地形查询(`TerrainSource`);
- 地砖物理属性配表(μ、灼烧、伤害)与屋顶层的进入判定;
- 水体 / 熔岩 / 粘液 的 2Hz 元胞自动机与相变,以及引水渠的汇水判定。

**本子系统明确不负责**

- 刚体积分、碰撞、举投 —— 属 WS-02(`server/src/physics/`);
- 房间识别、家具联动、温室判定 —— 属 WS-03(仅向它暴露 `hashCell()` 结构哈希);
- 电路通电求解 —— 属 WS-06(仅向它暴露 `wireAt()` 与 `setPoweredCells()`);
- 渲染、材质、粒子 —— 属 WS-09;本模块只产出 `TileView` 与脏位图;
- 网络同步策略 —— 属 WS-08;本模块只保证 `serialize()` 是 1024 字节定长。

**不负责的判定原则**:凡是「需要知道另一格状态才能决定」的逻辑,一律不放这里。例如「相邻小路自动平滑拼接边缘」(地砖 302 的 note)属于渲染层,本模块只提供邻格 FLOOR 值。

## 3. 数据结构

```ts
/** 视口格快照(渲染 / 调试桥接,不在物理热路径) */
interface TileView {
  gx: number; gy: number;          // 世界格坐标,整型任意范围
  lx: number; ly: number;          // 分片内坐标,0..15
  packed: number;                  // 原始 32-bit 单元,无符号
  elev: number;                    // 2 位,0..3
  base: number;                    // 4 位,0..15
  floorSlot: number;               // 6 位,0..63(FLOOR 层原始值)
  floorId: number;                 // 映射后的物品 ID,0 = 无铺装
  wire: number;                    // 4 位位掩码,0..15
  obj: number;                     // 12 位,0 = 空
  meta: number;                    // 4 位
  metaState: number;               // meta 低 2 位
  faceDir: number;                 // meta 高 2 位,0=北 1=东 2=南 3=西
  roof: number;                    // 旁路层屋顶 ID,0 = 无
  roofAlpha: number;               // [0,1],玩家站本格时生效的不透明度
  roofCovers: boolean;             // 头顶是否真有覆盖
  mu: number;                      // 摩擦系数 (0,1]
  burnPerSec: number;              // 每秒灼烧伤害
}

/** 地砖物理属性 */
interface FloorMeta {
  mu: number;            // (0,1],0.75 为缺省
  surface: SurfaceKind;  // INTERIOR / EXTERIOR / WET / ICE / CONVEYOR
  burnPerSec: number;    // >= 0
  walkable: boolean;
  canal: boolean;        // 引水渠候选
  hazard: boolean;
}

/** 元胞:1 满格 = CAP = 1000 毫格,整数域 */
class FluidField {
  amount: Int32Array;   // 0..1000,毫格
  base: Uint8Array;     // 基底层 ID
  solid: Uint8Array;    // 1 = 不可流入
  elev: Uint8Array;     // 0..3
}
```

## 4. 算法与公式

### 4.1 索引与坐标

```
idx(x, y)     = (y << 4) | x                       // y·16 + x,O(1)
chunkKey(cx,cy) = `${cx}:${cy}`
worldToChunk(w): cx = floor(w/16); lx = w - cx*16   // 负数自动归约
```

### 4.2 调色板映射(位宽硬约束的产物)

```
floorIdOfSlot(s) = PALETTE[s & 0x3f]
  PALETTE[0]     = 0            // 无铺装
  PALETTE[1..30] = 300 + s      // 301..330
  PALETTE[31..63]= 314          // UGC 像素地毯变体

floorSlotOfId(id) = id ∈ [301,330] ? id - 300
                  : id === 314     ? 31
                  : 0
```

### 4.3 流体:水面高度模型

核心是把「流动方向」编码成**标量水面高度**,而不是逐方向写条件:

```
surface(i) = elev[i] · (CAP + 1) + amount[i] + delta[i]
```

其中 `CAP + 1 = 1001` 是一级海拔台阶。这样:

- 任何更高海拔的格(哪怕只有 1 毫格)的水面都**严格高过**低一级的满格(1000 < 1001),于是「向下优先」自动成立,不需要单独分支;
- 同海拔时水面差 = 水量差,于是「向水量少的一侧扩散」自动成立;
- 引水渠(挖低成 Z-1)天然成为汇水口,零特殊逻辑。

每帧对每一对相邻格调用**一次** `fluxEdge(a, b)`,由 `surface` 决定谁是 src:

```
if surface(a) === surface(b): 不流(平局不搬运,避免同一条边来回震荡)
src = surface 较大的一侧;dst = 另一侧
if solid[src] or solid[dst]: 不流
if kind(src) === NONE: 不流
if kind(dst) ∉ {NONE, kind(src)}: 不流       // 异类流体不混,交给相变
avail = amount[src] + delta[src]             // 关键:按本帧已排出量结算
room  = CAP - (amount[dst] + delta[dst])
if elev[src] > elev[dst]:  f = min(avail, room)          // 有落差:整格倾泻
else:                      diff = avail - (amount[dst]+delta[dst])
                           f = min(avail, room, floor(diff · VISCOSITY[kind] / 2))
delta[src] -= f;  delta[dst] += f
```

**为什么必须用 `delta` 结算**:首版直接用 `amount[a]` 做 `avail`,同一格的水会被它的多条出边各流出一次,总量凭空增长(实测 1000 → 1500 → 2250)。加上 `delta` 后每格本帧的净额自动配对,`Σdelta ≡ 0` 恒成立,落账时不再需要 `clamp`,守恒是**结构性**的而非近似的。

复杂度:单帧 `O(min(budget, W·H))`,预算内每格处理 2 条边,常数约 40 次算术。

### 4.4 相变与账目

四邻接触后:

```
WATER      + LAVA → 黑曜石 110
HOT_SPRING + LAVA → 多孔浮石 111
SLIME      + LAVA → 黑曜石 110
前提:水侧 amount >= PHASE_MIN_AMOUNT (50 毫格)
```

相变抹掉**两格**存量,因此两条销毁量各自入账。守恒不变量:

```
total() + totalConsumedByPhase + totalConsumedLava === 初始总量
```

`grandTotal()` 就是这个和。只记水侧会漏掉熔岩存量 —— 含熔岩的池子会对不上账(实测差 4800),这是首版的实际缺陷。

## 6. 帧预算 / 性能

### 6.1 流体单帧处理格数 N 的推导

设单分片 256 格,视距半径 R=2 → 5×5 = 25 分片 = 6400 格。2Hz 帧预算 500ms,但流体只应占其中一小部分(渲染、AI、网络都要排队),取 **5%** = 25ms:

```
单格成本 ≈ 2 条边 × 20 次算术 ≈ 40 ops,在 JIT 优化后约 0.01µs
25ms / 0.01µs = 2.5×10⁶ 格/帧      // 纯算力上界

取实际安全系数 1/2400 → N = 1024 格/帧
```

`1024 = 2^10` 取整便于移位,且恰好等于 4 个满编分片(4×256),使 5×5 视距在 4 帧内被完整轮询一遍(游标轮转,见 `step()` 的 `cursor`)。

实测(`tests/WS-01.test.ts` 与手工基准):128×128 = 16384 格全图 `step()` 平均 **0.163ms**。按此推算 1024 格的单帧成本约 **0.010ms**,占 500ms 预算的 0.002%。**结论:预算给得极保守,真正的瓶颈是内存带宽而非算术。**

### 6.2 1GB 内存下的 chunk 常驻上界

```
单分片常驻 = 1024(cells) + 512(roofs) + 96(3×位图) = 1632 B
```

1GB 预算里地形最多占 1/4(其余给实体、流体网格、网络缓冲、AI):

```
256 MB / 1632 B = 164,482 个分片
```

而 16 人 + 40 野怪 + 1 Boss 同屏、视距 R=2 时只需 5×5 = 25 个分片:

```
25 × 1632 B = 40,800 B ≈ 39.8 KiB
```

即**实际用量是理论上界的 0.015%**,余量足够把视距拉到 R=20(41×41 = 1681 分片 ≈ 2.7 MB)。实测创建 4096 分片(64×64 区块、104 万格)峰值常驻 `6,946,816 B ≈ 6.6 MiB`,其中打包单元 4.0 MiB、屋顶 2.0 MiB、位图与 Map 开销 0.9 MiB。

### 6.3 序列化

4096 次 `serialize()`(每次 1024B)实测 < 3s 断言线内,单次约 0.02ms 量级;4 MB 全量传输在局域网 1Gbps 下约 32ms,可接受。

## 7. 异常与边界

| 场景 | 处理 |
| :--- | :--- |
| `get/set/withCell` 越界 | 抛 `RangeError`,**不静默钳制**(静默会让 bug 变成数据损坏) |
| `Chunk.deserialize` 缓冲 < 1024 | 抛 `RangeError` |
| `deserialize` 缓冲 > 1024 | 只读前 1024B,尾部填充忽略 → 向前兼容 |
| 入参是 `Uint8Array` 视图而非裸 buffer | `toBytes()` 归一化后再建 `DataView`(否则 `new DataView(u8)` 在某些宿主下抛错) |
| `FluidField` 尺寸非法 | 抛 `RangeError` |
| `step` 预算 ≤ 0 | 抛 `RangeError` |
| 水量注入越界/实心格 | 返回 0,不抛(注入是「尽力而为」语义) |
| 注入超过 `CAP` | 只接受剩余容量,返回实际注入量 |
| 相变水量 < 50 | 不触发 |
| 异类流体相邻 | 不混合,不搬运 |
| 分片不存在时查询 | 返回虚空默认格,且**不创建**分片 |
| 空输入 | `dirtyCells()` 空迭代;`serialize()` 全零 1024B |
| 网络抖动/丢包 | 幂等:同一 `serialize()` 反复发送结果一致;恢复靠 `deserialize` 全量重建,不依赖增量 |
| 断线重连 | 服务端持 `WorldGrid`,客户端全量拉取分片即可;`serializeSnapshot()` 保屋顶层与位图用于本地回滚 |

### 7.1 「虚空默认格」的高度 = Z0 地面,且只有一处定义(task-80)

`EMPTY_TILE`(虚空/越界默认格)的**唯一事实源在本模块的 `world/chunk.ts`**,
值为 `elev = Elevation.GROUND`(即 Z0 地面,`groundZ = elev − 1 = 0`)。

建造层 `build/grid.ts` 不再自己定义第二份,而是
`import { EMPTY_TILE } from '../world/chunk.ts'` 后 `export { EMPTY_TILE }`
(re-export 保持 `TileGridLike` 的越界契约对外不变)。

**为什么 elev 默认值不能是 0(必须取证,不能猜)**:

| 旁证 | 位置 | 说明 |
| :--- | :--- | :--- |
| 地面高度公式 | `physics/world.ts` | `该格地面高度 z = elev - 1`,故 `elev=0` ⇒ **Z-1 深沟**、`elev=1` ⇒ Z0 |
| 物理测试桩 | `physics/world.ts` 的 `FLAT_TERRAIN` | `elevAt: () => 1` —— 无地形时**假定 Z0 地面** |
| 分片构造 | `Chunk` 构造函数 | 未写格填充 `EMPTY_TILE`(elev=1)⇒ 新建分片即平地 |
| 演示世界 | `verify.ts` 建世界用 | `fillRect(8, 8, 39, 39, { floor: 1, elev: 1 })` |
| 深沟的产生方式 | `world/grid.ts` 的 `digToDeep` | **显式**写 `{ elev: Elevation.DEEP }` ⇒ DEEP 必须是「主动挖的结果」,不能是「没数据时的默认」 |

**改前的实测后果**(修复前两层各写一份字面量,值为 0 与 1):

```
captureBlueprint(收建造层 TileGrid)  越界/未写格 → 蓝图 elev=0(DEEP)
  ↓ buildRelayQueue        每格一个任务(含 255 个空格任务)
  ↓ WorldSim.startRelay → tickRelay   把 t.elev 写回世界
  ↓ this.setCell(x, y, { elev: t.elev })
实测:一张空的 16×16 蓝图把 256 格全挖成深沟;
      世界格 (3,3) 从 elev=1(groundZ 0)变成 elev=0(groundZ −1)
```

**钉住它的断言**(防再漂):

- `tests/WS-01.test.ts` 的 `Chunk 构造:...` 一条:
  断言 `EMPTY_TILE.elev === Elevation.GROUND`、`groundZ === 0`,
  并断言 `build/grid.ts` 的 `EMPTY_TILE` 与 `world/chunk.ts` 的**相等**
  (只断言「两处值相同」不够 —— 那允许把两处都写成同一个字面量,
  而**重复定义本身**才是根因)。
- `tests/WS-03.test.ts` 的 `WT-03-60` 一条:
  用生产函数 `captureBlueprint` 从一张**全未写**的建造层 `TileGrid` 描图,
  断言描出的空格 `elev === Elevation.GROUND`;并断言蓝图接力
  **不改动**落格处的地面高度。

两条断言都做过故障注入验证(注入后各自变红):
注入 ①`EMPTY_TILE` 改回 `elev=DEEP` ⇒ WS-01 47/50、WS-03 88/89;
注入 ②只在建造层恢复第二份定义 ⇒ WS-01 49/50、WS-03 88/89。

## 10. 未决问题

1. **`FLOOR` 槽位只有 64 个,地砖已有 30 种,UGC 占用 31~63。** 若后续地砖扩充到 40 种以上,UGC 余量会紧张。**待裁决**:是牺牲 UGC 变体数,还是把 OBJ 层的某些位借给 FLOOR?
2. **屋顶旁路层不进 32-bit 单元**,因此 `packTile`/`unpackTile` 往返**不包含屋顶**。若手册要求「屋顶必须能进 `TileFields` 往返」,需要升级冻结层签名 —— 本模块不改冻结层,已把需求记在此处。
3. **相变的熔岩侧销毁量**是否应该产出落物,还是完全湮灭?当前实现是「湮灭,只产出黑曜石/浮石方块」。若设计要「熔岩变蒸汽消耗掉」,需要新增第三笔账。
4. **`objIdAt` 把 351~371 当实心墙**用于 WS-02 碰撞,但 357 翠竹篱笆是「半高」围栏(原文),半高件理论上不该挡住弹道。**待裁决**:是否需要给物体加「阻挡高度」字段。
5. **流体的 budget 与游标轮转**在多人同时大量挖渠时可能出现「某片区域 4 帧才被服务一次」的感知延迟。是否需要按玩家距离加权调度,还是保持当前纯轮转的公平性?
6. **`serializeSnapshot` 的屋顶 RLE 在极端分散(每隔一格一个屋顶)时膨胀到 384B**,超过 512B 屋顶数组的压缩目标。是否改用固定 512B 原始布局换取确定性?
