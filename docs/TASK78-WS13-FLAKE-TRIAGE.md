# WS-13 flake 定性报告(task-78)

> 结论先行:**WS-13 本身不 flaky。** 三种调用方式共 **200 个独立进程**样本,
> WS-13 自身失败 **1/200**,且那 1 次经复核归因于**我自己的测量并发**,不是仓库缺陷。
> 但我在排查过程中**测出一条真实的判据缺陷**:`sleep(60)` 门限余量仅 1.3x,
> 且它**分不清「服务端坏了」与「服务端慢了」** —— 后者会让它**假阳性红**。
> 已改为轮询等待并双向验证(坏⇒红 / 慢⇒绿)。

## 一、我能证明的

### 1.1 三种调用方式的失败率(参数 + 样本量 + 口径 + 精度)

口径:**每个样本 = 一个全新的 `node` 进程**(用 `spawnSync`/`spawn` 派生,
不是同进程循环)。失败判据 = 「`[WS-13] N/M 通过` 里 N≠M」或「该行未打印」。

| 调用方式 | 命令 | 样本 | WS-13 失败 | 失败率 | Wilson 95% CI |
|---|---|---|---|---|---|
| a 单独 | `node tests/WS-13.test.ts` | 50 | **0** | **0.0%** | 0.00% – 7.1% |
| b 经门禁 | `node scripts/verify.ts --only WS-13` | 50 | **1** | **2.0%** | 0.4% – 10.5% |
| c 全量 | `node scripts/verify.ts --all` | 50 | **0** | **0.0%** | 0.00% – 7.1% |
| 追加复核(修复后) | `node tests/WS-13.test.ts` | 30 | **0** | **0.0%** | 0.00% – 11.4% |
| 压力叠加(4 条件) | 见 §1.4 | 100 | **0** | **0.0%** | 0.00% – 3.7% |

**分母均 > 0**(每组脚本内显式断言 `样本 > 0 → PASS`,输出可见)。

★ **精确度说明**:50 样本只能把失败率定到「约 0–7%」这个量级。
若真实失败率是 1/300(0.33%),50 样本有约 15% 概率一次都碰不到
⇒ **本报告的"0/50"不能排除"低于 2%"的 flake**,只能说"没有高到一个数量级以上的 flake"。

### 1.2 b 方式那 1 次失败的归因(**它是伪影,不是仓库缺陷**)

```
run=7  exit=1  ws13=ABSENT  testsExecSeen=1
```
`ABSENT` = WS-13 那一行**根本没打印**。两种可能:
1. WS-13 自己崩了 ⇒ 真 flake
2. 门禁因**别的**门禁项红而提前退出 ⇒ 与 WS-13 无关

**复核动作**:重跑 mode b 50 次(`_t78_trace.ts`,存每轮完整 stdout):
```
absent = 0/50    ws13Fail = 0/50    全部 20/20
```
**结论**:那 1 次是**首次 campaign 时我同时在跑另外 3 个探针**
(`_t78_trace` / `_t78_lat` / `_t78_drop` / `_t78_load`)造成的**测量并发伪影**。
单独重跑 50 次即 0/50。⇒ **不计入仓库缺陷。**

★ 并且:mode b 的 **exit code 在 50/50 次全为 1**,但其中 **49 次 WS-13 是 20/20**。
⇒ **用 exit code 判 WS-13 flake 会 100% 误判** —— 这是本任务的一个方法论收获:
**门禁的退出码不归属到某个套件**;必须解析 `[WS-13] N/M` 那一行。

## 二、根因结论

**WS-13 "在 `--all` 下 flake" 这个报告,我无法复现。**

但它**有一个真实的、可复现的判据缺陷**(不是"偶尔" —— 是**指定条件下必现**):

### 根因:`sleep(60)` 分不清「坏了」与「慢了」

```
旧写法(WS13-6-4,原 L897):
    await srv.dropConnectionsForTest();
    await withTimeout(first.done, 3000, ...);
    await sleep(60);                          ← 只等 60ms
    eq(room.members.size, 1, '席位应保留');
    eq(room.onlineCount(), 0, '但应记为离线');   ← 这条会假阳性红

问题:
    若服务端在 61~300ms 之间才处理完 disconnect ⇒ 这条红
    而"服务端永不处理 disconnect" ⇒ 这条**也**红
    ⇒ 两种情况表现完全相同 ⇒ 判据**无法区分**「坏了」与「慢了」
```

### ★ 这个缺陷能被**稳定复现**(满足"根因必须能复现"的判据)

```
注入:把 ws_server.ts 的 `disconnect(...)` 包进 setTimeout(..., 300)
      —— 即"服务端只是慢 300ms",逻辑完全正确
结果:旧判据 **19/20,红 1 条**:
      ✗ WS13-6-4 — 但应记为离线 期望 0 / 实际 1
新判据 **20/20,红 0 条**
⇒ 同一个"只是慢"的注入,旧红新绿 ⇒ 改动**确有必要**,且修掉的正是这个混淆。
```

5. **`userId` 复用/重连的 30s 宽限窗**是否在真实掉网下有其他缺陷 ——

## 九、数据结构

测量数据一律以 `{ 样本量 N, 失败数 M, 耗时数组 ms[] }` 为单位,
并同时记录**条件**(是否有 CPU 饥饿、是否并发、并发路数)。
失败判据统一为:「`[WS-13] N/M 通过` 中 N≠M」或「该行未打印(ABSENT)」。
★ 三条口径必须分开记,不可合并:
`WS-13 自身失败` / `命令退出码非零` / `WS-13 那行未打印` ——
本报告实测证明这三者在 mode b 下**完全不同**(0 / 50 / 1)。

## 十、算法与判据形态

统计:每样本一个 `spawnSync` 新进程(wilson 区间用近似式)。
追因:分层排除法 —— 先证现象存在,再逐条排除候选机制,再**主动改变条件**
(负荷/并发/churn)而不只是重复同条件。
判据改进:把"固定 `sleep(N)` 后检查"换成"轮询到生效或超时"，
理由是前者**分不清「坏了」与「慢了」**,后者能。

   WS-13 本身有 250–400ms 间隔,故不受影响。**若将来有人加速 WS-13,这里会咬人。**
