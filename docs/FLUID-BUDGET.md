## 2. 接口

```ts
class FluidField {
  step(budget = FLUID_CELL_BUDGET): FluidStepReport
  addWater(x, y, units, base?): number      // 返回实际注入量
  amountAt(x, y): number
  total(): number
  markActive(i: number): void               // 标该格及四邻为活跃(内部用,也供辅助函数用)
  get activeCount(): number                 // 观测用
}

interface FluidStepReport {
  processed: number;      // 本帧处理的格数
  moved: number;          // 本帧转移的毫格(单边计一次)
  phaseChanges: number;
  consumedByPhase: number;
  consumedLava: number;
  truncated: boolean;
}
```

## 3. 数据结构

| 结构 | 类型 | 说明 |
| :--- | :--- | :--- |
| `amount` | `Int32Array` | 毫格存量。**唯一真相** |
| `base` / `solid` / `elev` | `Uint8Array` | 流体种类 / 实心 / 海拔 0..3 |
| `deltaBuf` | `Int32Array` | 通量暂存,**跨帧复用**(见 §6) |
| `activeArr` | `number[]` | 活跃格列表(**不是 `Set`**,见 §4.3) |
| `activeIdx` | `Map<number, number>` | 格 → 在 `activeArr` 的下标,用于 O(1) 去重与摘除 |
| `activeCursor` | `number` | 活跃列表的轮转游标 |
| `cursor` | `number` | 全图游标(兜底路径) |

**活跃集合是缓存,不是真相**。`amount` 永远是唯一真相。缓存漏了某格,
后果只是它这一帧不流动(游标会补上),**不会算错** —— 这个性质让该优化
不可能破坏守恒。

## 4. 算法

### 4.1 通量

每对相邻格只算一次(右邻 + 下邻),方向由**水面高度**决定:

```
surface(i) = elev[i] × (CAP+1) + amount[i] + delta[i]
```

水面高的一侧流向低的一侧。海拔以 `CAP+1` 为一级台阶,保证「先向低处流」
严格优先于「同海拔铺平」—— 高一级的格即使只装 1 毫格,水面也高过下一级满格。
于是引水渠(挖低成 Z-1)天然形成汇水口,不需要特殊分支。

### 4.2 一帧的顺序

```
step(budget):
  ├─ phasePass()          相变(只扫活跃格)
  ├─ fluxPass(limit, ...) ① 活跃格轮转 ② 游标补齐剩余额度
  └─ 落账(只遍历本帧被改过的格,并清零 delta)
```

### 4.3 为什么活跃格是数组而不是 `Set`

**这是本项目踩过的最贵的一个坑。**

`Set` 按插入顺序遍历,而每帧 `limit` 有限。当活跃格数超过 `limit` 时,
**排在后面的格永远轮不到**。实测后果:

水在 64×64 里铺平后活跃集合有 1160 格(> `FLUID_CELL_BUDGET` 1024)。
此时在空白处注入 500 毫格新水 ——

| 帧 | `moved` | 注入格水量 | 邻格水量 |
| ---: | ---: | ---: | ---: |
| 1 | 0 | 500 | 0 |
| 2 | 0 | 500 | 0 |
| 3–5 | 0 | 500 | 0 |

水**原地不动**,而活跃集合里有 1160 格。新格插在 1160 个老格之后,
`done >= limit` 已成立,它永远轮不到。

**这不是平衡,是停顿** —— 两者在 `moved === 0` 时表现相同,必须靠
「邻格水量差」区分(见 §9 诊断方法)。

改成数组 + 轮转游标后,每格都在 `ceil(size / limit)` 帧内被轮到,
**与它何时被插入无关**。

### 4.4 摘除后必须重新入队

摘除是为了让轮转能前进(否则数组头部被重复访问)。但「任何 `amount > 0`
的格都留在活跃集合里」是 `phasePass` 的**正确性前提** —— 静态的水若被
摘掉,它紧挨熔岩时的相变将**永不触发**,且不报错。

所以摘除后立刻按「是否仍需处理」重新入队:有水或四邻有水 → 入队;
彻底干涸且四邻也干 → 不入队(自然淘汰,集合不会无限增长)。

## 5. 为什么改:US4 的诊断方向是错的

`docs/SIM-orchestration.md` §10 US4 写道:

> **流体预算在大世界偏低** — 1024 格/慢帧,512×512 世界铺满需 128 秒。
> 建议按玩家距离加权或提高预算。

实测推翻了「预算偏低」这个判断:

| 世界 | 每步耗时 | 占 500ms 慢帧预算 |
| :--- | ---: | ---: |
| 256×256 | 0.26 ms | 0.05% |
| 512×512 | 0.99 ms | **0.2%** |
| 1024×1024 | 3.9 ms | 0.8% |

**CPU 完全不是瓶颈。** 而且「空/有 = 99%」—— 空世界的 `step` 成本与有水的
世界几乎相同,说明成本几乎全是**固定开销**,与水量无关。

真瓶颈是**覆盖延迟**:纯轮询下,一格被访问的间隔 = `n / budget` 慢帧。

| 世界 | 全图一轮 | 实测:水从 y=2 铺到 y=27 |
| :--- | ---: | ---: |
| 64×64 | 4 慢帧 | 39 秒 |
| 128×128 | 16 慢帧 | **2268 秒(38 分钟)** |
| 256×256 | 64 慢帧 | 未在 2500 秒内收敛 |

水的**前沿**每帧最多推进 1 行,而前沿所在的行要等轮询转到才被处理。
世界越宽,一帧覆盖的行数越少(`budget / width`:64→16 行、128→8 行、
512→**2 行**),所以纵向扩散随世界尺寸急剧变慢。

**「提高预算」治不了它** —— 调到 4 倍只是把 128 秒变成 32 秒,
而每帧成本线性上升。瓶颈是**访问顺序**,不是预算大小。

### 修复效果

| 世界 | 修复前 | 修复后 |
| :--- | ---: | ---: |
| 64×64 | 39 秒 | 28.5 秒 |
| 128×128 | **2268 秒** | 32.0 秒 |
| 256×256 | >2500 秒 | 32.5 秒 |
| 512×512 | >2500 秒 | 31.5 秒 |
| 1024×1024 | 未测 | 32.0 秒 |

**四个数量级的世界,扩散耗时一致。** 同一场景的结果也一致
(最深 y = 27,湿格数 ≈ 3040)。

## 6. 性能

消除的三处 O(世界面积):

| 处 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 落账循环 | `for (i = 0; i < n; i++)` 扫全图 | 只遍历本帧被改过的格 |
| `phasePass` | 每帧扫全图找「水+熔岩接触面」 | 只扫活跃格 |
| `delta` 数组 | 每帧 `new Int32Array(n)`(1024² = **4MB/帧**) | 复用 `deltaBuf` |

实测(同场景:大世界里一小片水):

| 世界 | 修复前 | 修复后 |
| :--- | ---: | ---: |
| 64×64 | 0.098 ms | 0.126 ms |
| 512×512 | 0.825 ms | **0.125 ms** |
| 1024×1024 | 3.026 ms | **0.120 ms** |

> 注:64×64 反而略慢(0.098 → 0.126)是活跃集合的 `Map` 维护成本在
> 小世界下的净开销。这是**刻意的取舍**:小世界绝对成本极低(0.13ms),
> 而大世界从 3.0ms 降到 0.12ms。若将来小世界成为热点(大量小房间),
> 可加「世界面积小于阈值时跳过活跃追踪」的分支 —— 但当前无证据需要。

## 7. 边界

| 情况 | 行为 |
| :--- | :--- |
| `budget` 非正整数 | 抛 `RangeError` |
| 越界坐标 `addWater` | 返回 0,不抛错 |
| 实心格注入 | 返回 0 |
| 注入超过 `CAP` | 只注入余量,返回实际量 |
| `n <= budget` | `truncated = false`,处理全部格 |
| 活跃集合为空 | 全部走游标路径(行为等同于修复前) |
| 相变后变实心 | 标活跃(邻居仍可能注水进来,只是流不进去) |
| 净变化 ≠ 0 | 抛错(不静默夹紧) |

## 8. 耦合

| 上游 | 提供 |
| :--- | :--- |
| `shared/types/tile.ts` | `BaseFluid` / `Elevation` / `CAP` |
| `WorldGrid` | `solid` / `elev` / `base` 的来源(靠 `setCell` 显式同步) |

| 下游 | 用途 |
| :--- | :--- |
| `WorldSim.tick` | 每慢帧 `fluid.step(this.fluidBudget)` |
| `FluidField.drainPhaseProducts()` | 取出相变产物(黑曜石/多孔浮石),由编排层 `WorldSim` 每慢帧调用后**写回 OBJ 层** |

**相变产物的交接必须由编排层显式 drain**(`WorldSim` 慢帧里
`for (const p of this.fluid.drainPhaseProducts()) this.setCell(p.x, p.y, { obj: p.obj })`)。

这一环曾经**缺失**:`phasePass()` 只往 `pendingObj` 里 push,却**无人取走** ——
后果是玩家把水浇到熔岩上**看不到黑曜石**,且数组无界增长。
本表早先写的 `pushPendingObj` **在全仓并不存在**(一个从没被实现的函数名),
正是这种「文档承诺了一个不存在的交接口」让缺口长期看不出来:
读文档的人会以为已经接好了。现已改为指向真实存在、且真的被调用的 `drainPhaseProducts()`。

回归断言见 `tests/WS-FND-07.test.ts`:`WF-07-01` 查**地形**该格是否真变成
`OBSIDIAN_ID`,而不是查 `pendingObj.length`(后者在缺陷状态下也会增长,
用它做断言会「通过」却什么都没修好);`WF-07-02` 查队列有界。

**`WorldGrid` 与 `FluidField` 的双份状态**仍是未决 US5:靠 `setCell` 同步,
更稳的做法是让 `FluidField` 读 `WorldGrid`,但那要改 WS-01 的实现选择且
增加每格查表开销。

### 诊断方法:`moved === 0` 不足以判定平衡

「停顿」与「真平衡」在 `moved === 0` 时**表现相同**。区分方法:

1. 数「水平相邻且水量差 > 阈值」的边(`不均边`)。真平衡时它应为 0;
   停顿时它很大。实测停顿场景:帧 1000 起 `moved=0` 而**不均边 = 0**
   (那是真平衡);冻结 bug 的表现是注入新水后 `moved` 仍恒为 0。
2. **在空地上注入少量水,看它是否立刻流。** 这是最直接、最难自欺的判据。

## 附:修这个 bug 时我引入又修掉的 3 个自身错误

诚实记录,因为它们都是「不报错但行为错」类:

1. **`touched` 用数组不去重** → 同一格以三种身份被推入,落账时重复累加,
   抛出**误报**「流体守恒被破坏:净变化 557 毫格」。守恒本身没坏,
   坏的是「哪些格被改过」这份名单。
2. **越界索引进 `touched`** → `i + width + 1` 在最后一行越界,
   越界读得 `undefined`,`net += undefined` 变 **NaN** → 报「净变化 NaN 毫格」。
3. **越界索引进 `touched` 的 NaN** 也是我最初把探针写成 `f.steps0` 的同一类错:
   **仪器/代码的错会被误读成被测对象的错。** 所以每次报错先问「是它坏了,
   还是我的检查方式坏了」。
