## 二、复核方法

### 2.1 注入器设计(为什么它本身也要防错)

对抗性复核最大的风险是**复核者自己留下改动**。因此注入器做了三道保护:

1. 读入为 **Buffer**(字节级),还原时原样写回 —— 避免文本编码往返损坏。
2. 注入与还原包在 `try/finally` 里,即使测试进程崩溃也必然还原。
3. 还原后重算 SHA-256 与注入前比对,不一致立即报错并中止。

### 2.2 判定标准

- **有区分力**:改坏真实源码后,至少一条**相关**断言变红。
- **装饰**:无论怎么改都不红。
- 中间态必须如实分级:「**灵敏度低**」(能红,但要极端恶化)与「**恒真**」(永远不红)是两回事。

### 2.3 一处方法修正

首次做 G1 的 `migrationNote` 注入时,我改的是**类型声明行**(第 251 行)而非**校验逻辑**(第 274 行),
结果全绿。这是**无效注入**,不是断言装饰 —— 我随后重做才得到有效结论(§4.2)。
这类「注入点选错 ⇒ 误判为装饰」是复核中最常见的假阴性来源,故单列说明。

## 四、G1(alchemy-core):H1–H4 是自证式,但外围断言经真实注入验证有效

### 4.1 先说观察到的结构问题

阅读 `tests/WS-FND-04.test.ts` 第 477–543 行发现:H1–H4 **不碰任何真实源码**。

```
H1–H4 段含文件写入 API : false
H1–H4 段含子进程调用   : false
```

它们的做法是:在测试内部**重新实现一个坏版本**(如 `badLayout`、`wrongCapacity`、`badAudit`、`badDetect`),
然后断言「坏版本确实坏」。例如 H3:

```ts
const badAudit = (exts) => { /* 故意漏掉 migrationNote 检查 */ };
eq(badAudit(needsNote).length, 0, '坏校验必须漏掉这个问题 —— 否则本次注入无效');
ok(auditExtensions(needsNote).length > 0, '真实校验必须抓住它');
```

**这能证明什么**:真实校验对**构造的输入**有区分力(第二行)。
**这不能证明什么**:真实源码一旦被改坏,套件是否会红。前者是「函数对输入的敏感性」,后者是「回归守卫的有效性」——
**自测者用自己的假设验证自己的假设**,正是本任务要防的模式。

所以 H1–H4 只能算**判据自检**,不能算**故障注入**。这一点与文档措辞(同为「故障注入」)存在语义落差。

### 4.2 于是我改成真实注入 —— 结果:H1–H4 对应的判据全部有效

| 我的真实注入 | 目标文件 | 实测变红 | 裁决 |
| :--- | :--- | :--- | :--- |
| 去掉 `needsMigration`/`migrationNote` 校验 | `server/src/content/baseline.ts` | **C9-1 + H3** | ✓ 有效 |
| `OBJ_CAPACITY_FROM_FROZEN` 漏掉 `>>> OBJ_SHIFT` | `scripts/extension-drill.ts` | **A1 A2 B2 B3 B4 C1-3 C2-1 C3-1 C3-2 C3-3 C4-1 C5-2**(12+ 条) | ✓ 极强 |
| `computeSlotLayout` 产生半行(`rows + 0.5`) | `client/src/ui/inventory.ts` | **C1-1 + C1-4** | ✓ 有效 |

**第 2 项特别值得记录**:这正是本项目踩过的真实坑(`OBJ_MASK` 当容量推出 268369920,大 6 万倍)。
我复现坏常量后,套件一次变红 12 条以上,报错信息还直接点出「期望 4095 / 实际 268369920」。
**这个坑现在有真正的守卫了。**

### 4.3 一处诚实更正:`rowAligned` 不是恒真

我从 `client/src/ui/inventory.ts:103` 读到 `rowAligned: slots % spr === 0`,而 `slots = rows * spr`,
初步假设它恒真(「`(rows*spr) % spr` 数学上必为 0」)。**这个假设错了**,必须更正:

- 注入 `rowAligned: true`(硬编码)→ 全绿。但这**不能**推出恒真结论:在正确实现下 `rows` 是整数,此改动是**等价变换**。
- 注入 `contentRows = n / spr`(不取 `ceil`,制造真半行)→ `n=1` 时 `rows=1.0625`、`slots=17`,
  `17 % 16 = 1` → `rowAligned=false` → **被 WS-09:1644 抓住**。
- 穷举 216 组合法整数输入,`rowAligned` 无一为假;但**非法输入**(`NaN`/`Infinity` 的 `slotsPerRow`)下它确实为假。

**裁决**:`rowAligned` 是「正确实现下恒真、实现退化时能变假」的回归守卫,**不是装饰**。
它的价值不在当前代码,而在将来有人改坏 `rows` 计算时。

### 4.4 G1 裁决

H1–H4 的**方法**是自证式的(不碰真实源码),但**被它们保护的判据本身经真实注入验证有效**。
即:结论对,方法弱。建议在文档里把 H1–H4 的措辞从「故障注入」改为「判据区分力自检」,以免读者误以为它们验证了回归路径。

**一次注入命中多条断言**说明判据之间有交叉覆盖,不是单点依赖 —— 这是好信号。

### 5.2 计时断言:不是恒真,但灵敏度低(如实分级)

这是最需要警惕的一类(计时断言最容易退化成永远绿)。我用人造忙等扫描临界点:

| 注入强度 | 41 刚体 `maxMs` | 阈值 12.5ms | 结果 |
| :--- | ---: | :--- | :--- |
| 无注入 | 0.103 | — | 绿 |
| 40 000 次 `sqrt`(≈8× 减速) | 0.344 | — | 绿 |
| 800 000 次 | 未超 | — | 绿 |
| **5 000 000 次**(≈600×) | **17.04** | > 12.5 | **✗ 红** |
| 12 000 000 次 | 39.67 | > 12.5 | ✗ 红 |
| 30 000 000 次 | 99.17 | > 12.5 | ✗ 红(并连带 117 刚体那条也红) |

**裁决:有区分力,非装饰;但需要约 600× 的性能恶化才触发。**

这是一个**刻意的权衡**,不是疏漏:任务要求「计时类断言必须留足余量,避免机器抖动导致偶发红」。
收紧阈值能提高灵敏度,但会在负载下假红 —— 我实测过 12 路 CPU 竞争下 3 次全绿,正是余量换来的。
把灵敏度做成 600× 意味着:**只有物理慢到肉眼可感(单帧 17ms 占 50ms 预算 34%)才会报警**,
而那种程度已足以让 20Hz 掉帧。这个折中我认为合理,但**必须写明**,否则读者会误以为它能捕捉 2× 级别的性能回归。

这是**两个缺陷叠加**的场景,单点注入法在原理上覆盖不到。登记为已知边界,不作为缺陷。
