## 二、排序原则(为什么这么排)

四条硬约束,按优先级:

1. **先修缺陷,再接线。** 接线会把代码路径暴露给玩家,此时已知缺陷的影响面从「理论」变「可触发」。
2. **先服务端,后客户端。** 客户端缺入口是**结构性**的:`client/` 16 个文件无 `main`/`index`/`.html`,
   且 `package.json` **无构建步骤**(15 个 script 全部是 `node xxx.ts`)。
   而 14/16 的 client 模块**无外部依赖** ⇒ 缺的是「如何把 TS 送到浏览器」这个**决策**,不是代码量。
   服务端接线不依赖它。
3. **先闭环,后铺量。** 优先让一条「采集 → 合成 → 战斗 → 掉落」的最小循环真正跑通,
   而不是把 25 个模块平铺接完。
4. **每接一个,门禁数字必须降。** 否则说明接的是假线。

### 阶段 4:客户端(预计 3~5 个工作单元)—— **需先做一个决策**

**这是全项目唯一真正的「决策点」,不是工作量问题。**

现状矛盾:
- `client/` 16 个文件,**无入口**;
- `package.json` **无构建步骤**(零依赖原则,只有 devDep typescript);
- 但浏览器**不能直接跑 `.ts`**;
- 14/16 模块**无外部依赖**(只有 `three/*` 需要 `three`)。

三条路,选一条:

| 方案 | 做法 | 代价 | 我的看法 |
| :--- | :--- | :--- | :--- |
| **A. 加一个极简构建** | 用 `esbuild`/`vite` 只做 bundle,不做别的事 | 破坏「零构建步骤」原则;但只是**构建**阶段,运行时仍零依赖 | **推荐**:原则的目的是「不用 ts-node 就能跑测试」,那个目的不受影响 |
| B. 运行时转译 | 浏览器里用 `esbuild-wasm` | 首屏慢、体积大 | 不建议 |
| C. 用 Node 自带的 `--experimental-strip-types` 服务端渲染 | 不现实(需要 DOM) | — | 不可行 |

**选 A 的具体做法**:`esbuild --bundle client/src/main.ts --outfile=public/app.js`,
`main.ts` 由我写(约 200 行装配层,把 16 个模块连起来)。
`package.json` 加 `"build:client"`,**不是** `"build"` —— 保持「服务端零构建」。

## 五、我做计划时刻意避开的坑

1. **不按 WS 顺序接。** WS 编号是**文档顺序**,不是依赖顺序。
   实际依赖是:战斗 → 掉落 → 背包 → 存档(阶段 1),而不是 WS-01..11 顺序。
2. **不追求「50 条全部清零」。** 阶段 4 之前,client 那 16 条**不可能**降 ——
   在构建决策未定前接不了。把它们报成「待接线」是对的,但它们的时间线**取决于一个决策**,
   所以单列。若决策迟迟不定,它们会**永远**留在账上 —— 这是必须让 owner 看见的事实。
3. **不把「写了代码」当完成。** 完成的标准是**门禁数字下降 + 端到端可验证**。
   本会话已经踩过 8 次「完整实现、单测全绿、编排层不接」,不能再造第 9 个。
