## 〇 先说清"这个决定到底在决定什么"

我有意把三个方案**放在同一个坐标系里**比较,而不是各说各的代价。那个坐标系是:

```
玩家按 W ⇒ 屏幕上要发生什么 ⇒ 服务端要收到什么 ⇒ 协议里要有什么字段
```

★ 而侦察查出的**第一条决定性事实**(两位队友独立发现、我复核)是:

```
客户端 boot.ts 里 'players' 出现 **0 次**
⇒ 客户端**根本不渲染任何玩家/角色实体**
⇒ ⇒ 无论选哪个方案,**在"客户端画出角色"这件事做完之前,都看不出移动**
```

我把这一条放在最前面,因为它**同时改变三个方案的代价**:
```
· 它让"接通输入链路"的价值打折 —— 接通了也看不见
· 它让"方案三(点击移动)看起来能复用现成反投影"这个优势变小
  (落格能力有了,但落格之后仍然没有东西可以走过去)
· 它是**三个方案的共同前置**,因此**不该计入任何一个方案的差异代价**
```
⇒ 我下面每个方案都**单独列出**「共同前置」与「方案差异」。混淆这两者会让对比失真。

**共同前置(三方案都要做,已实测确认缺失)**:
| 项 | 现状 | 实测证据 |
| :--- | :--- | :--- |
| 客户端渲染玩家实体 | **无** | `boot.ts` 含 `players` 0 次;造可见物仅 chunk/roof/立牌 |
| 客户端有"角色位置"概念 | **无** | 全客户端只有 `pan`(相机);`playerGx/Gy` 被改为**服务端权威**(task-67 S2,`boot.ts:1069`) |
| 服务端收到位置后确有权威写入 | **有** ✓ | `room.ts:1278 applyMove` 真写 `p.x/p.y/p.z`(verify.ts:3341 实测) |
| 服务端校验位置合法性 | **有** ✓ | `anticheat.ts:525 checkMove`,判 `dist > allowed` |

⇒ ★ **共同前置的实际工作量**:一个"玩家可见物 + 位置插值到网格"的渲染层。
   它不是三个方案的差异,但**没有它,三方案都无法验收**(只能靠日志证明)。

### 方案乙:WASD 改为**驱动角色**(输入链路全通)

**要建的东西(逐层,实测数字)**:

| 层 | 缺什么 | 现状证据 | 量级 |
| :--- | :--- | :--- | ---: |
| 客户端输入翻译 | 键鼠 → `InputCmd{seq,moveX,moveY,jump}` | `boot.ts` 含 `InputCmd` **0** 次;`keys` 12 处、`pan.` 22 处 | 新写 ~80-150 行 |
| 客户端上行 | `session.send()` 的**生产调用点** | `session.send` 定义在 `session.ts:337`,生产调用 **0**(`:266` 是 hello) | 新写 ~30-60 行 |
| 协议 | `ackedSeq` 字段 | `wire.ts` 367 行:含 `ackedSeq` **0**、`inputSeq` **0**、`InputCmd` **0** | **改协议** |
| 协议 | 输入帧种类 + `ackedSeq` | 全仓**找不到** `ClientFrame` 定义;客户端只发 `'hello'` | **改协议** |
| 服务端 | 收输入帧并解析 | `ws_server.ts:591` **只 log 不解析**(其注释:"真接生产时在此交给 decodePacket") | 改服务端 ~50 行 |
| 服务端 | 输入序号确认下行 | `anticheat.ts:250` 回 `corrected:{x,y,z}`,**不含 seq** ⇒ `resimulate` 缺基准 | **改协议** |
| 反作弊 | `checkMove` 是否要改 | ★ **取决于语义裁决**(见下"更正") | 0 或重设计 |
| 语义 | 服务端是否独立模拟玩家 | `world_sim.ts:2176`:"本方法**绕过积分**,不自动获得摩擦/传送带/碰撞反弹。**这是刻意的**" | **设计裁决** |

**★ 一条我必须更正的说法(重要)**

我在草稿里据 mob-boss-ai 的转述写过:「位置方案 ⇒ `reconcile` 恒 IGNORE ⇒ 预测层等于没工作」。
**我读了源码,它说的方向相反。** `world_sim.ts:2153-2178` 的原文是:

```
## 为什么是「位置」而不是「速度」
1. **速度方案与客户端预测永久对不上**。`prediction.ts:70-82` 的 `predictStep`
   算的是 `v * DT`:客户端预测 4.5 × 0.05 = 0.2250 格/帧,
   而服务端写 vx=4.5 ⇒ 实测一帧 dx=0.1620,vx 衰减 4.5 → 3.24 ⇒ **差 28.0%**
   ⇒ 在速度方案下 reconcile 会持续 SMOOTH/SNAP。
2. 反作弊上界 maxDisplacementPerTick() 是**位移**量纲,checkMove 判的也是 dist(新旧坐标)。
3. 本仓既有先例全是「直接写位置」。
```

★ 我**实测复核了那个 28.0%**:`(0.2250 − 0.1620) / 0.2250 = 28.0%` ⇒ 与注释一致 ✓
   ⇒ 但它**是"速度方案"下的失配值**,不是"位置方案"的。

```
⇒ 正确的结论:「位置方案**刻意**让客户端预测与服务端权威对齐,故 reconcile 不出修正」
   这是**设计目的达成**,不是"预测层没工作"。
   客户端预测的价值是"按键立即动,不等往返",而 IGNORE 正是它**准**的证据。
⇒ mob-boss-ai 认对了机制(采纳客户端坐标确实会让回滚逻辑无事可做),
   但**归因反了**:源码把这件事写成"刻意选择",它写成了"缺陷"。
   ★ 而它自己在报告里把这条标为"推论,不是实测" —— **它的谨慎标注救了我**:
     我因为它标了"推论",才会去读源码;否则我会直接把它当结论。
```

⇒ ★ **对方案乙的真实含义(更正后)**:
```
问题不是"预测层没用",而是:**服务端只做"带速度上界的采纳",不独立模拟玩家**。
⇒ 于是 `resimulate`(按 ackedSeq 重演)缺少"要重演到什么"的独立基准。
⇒ 这是**设计取向**(信任客户端 + 上界约束)与**预测回滚**这套机制之间的取舍,
   不是"做了也白做"。若要走方案乙,这才是需要裁决的那一条。
```

**代价汇总**:
```
改代码:client 3-4 文件 + server 2 文件 ≈ 200-400 行新代码
改协议:shared/types/wire.ts(至少 +3 字段/帧种类)  ★ 跨端一致,必须一次做对
改测试:WS-07(5439 行)要加真链路断言;WS-12/WS-13 可能受影响
门禁数字:白名单 14→13,欠账 8→7,可达 +1
★ 但**数字变化小、实际工作量大** —— 这是最典型的"数字不反映代价"
风险:协议改动若与 client-stage 在改的 client/src/net/** 冲突 ⇒ 需要串行
```

## 三 我的建议(不是裁决 —— 裁决权在你)

**我建议先做「甲」,但只做其中的第 3 项(订正两处错误文本),然后把乙/丙合并成一张"输入语义裁决"CR。**

理由:

```
1 ★ 当前最贵的不是"没接线",而是"两处错误文本在误导复核者":
    · 白名单理由说"等客户端网络层",而网络层**在岗**(session.ts:145 有 WebSocket)
    · 白名单理由说"WS-08 套件号",而实现测试在 WS-03
   ⇒ 我已实测这两条。订正它们**0 行代码、0 数字变化**,但让下一个人的判断基于事实。

2 ★ 方案乙背后有一条**已写明的设计取向**:服务端「绕过积分、直接采纳客户端坐标,
   靠 checkMove 的上界约束」(`world_sim.ts:2156-2178` 自述,并给了 28.0% 的实测依据)。
   ⇒ 而这条取向与 `prediction.ts` 里 `resimulate`(按 ackedSeq 重演)**前提不同**
     —— 前者假设"客户端算得对",后者假设"客户端会漂、需要重演修正"。
   ⇒ 两种假设可以共存,但**必须先讲清楚谁在什么条件下生效**,否则接线后会出现
     "同一套代码里两个互不承认的权威"。而协议改动是全仓最贵的改动
     (跨端一致 + 需重跑集成 38 条)。
   ⇒ 应该**先裁决语义,再动协议**。

3 ★ 共同前置(客户端渲染玩家)是**独立的一步**,且它能被单独验收:
   即使不接输入,先让"服务端权威位置 → 屏幕上有个东西"也能跑通 ——
   而它**恰好也是甲乙丙都要的那一步**。
   ⇒ 建议把它**独立成一张卡**,不绑在语义裁决上。
```

**如果你要我推进,我建议的顺序**:
```
第 1 张卡:订正两处错误文本(0 代码)              ← 现在就能做,无风险
第 2 张卡:客户端渲染玩家实体 + 位置插值(共同前置) ← 可独立验收
第 3 张卡:输入语义裁决 CR(乙 vs 丙)              ← 拿到第 2 张的实际手感后再定
```
★ 而**第 2 张卡做完之前,我不建议碰协议** —— 因为手感会改变裁决,
  而协议改动最贵、最不该返工。
