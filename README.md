> ### ⚠️ 为什么必须带那两个 `--strict-*`(2026-11-12 实测)
>
> 裸 `node scripts/verify.ts` **也会印「全部通过」并返回退出码 0**,
> 即使此刻刚刚新增了没登记的不可达模块 —— 因为可达性与同义反复这两道门禁
> 在默认口径下**只告警、不拦截**,而告警写在 stderr、不进汇总行。
>
> ```
> 造一个「新增未登记的不可达模块」后:
>   node scripts/verify.ts                   → 全部通过 · 6363ms   退出码 0
>   node scripts/verify.ts --strict-reach    → 1 项失败 · 6309ms   退出码 1
> ```
>
> ⇒ 「`verify.ts` 全绿」**并不覆盖这两道门禁**。本文件此前把裸命令写成
> 「唯一的完成定义」,那是一个**以最权威口吻说出的不完整断言** ——
> 而 `docs/PROGRESS.md` 的工具陷阱又教人「看『全部通过』这行」,
> 两句话合起来会把「新增欠账」读成「完全干净」。
>
> 现已收紧:未拦截的告警会**出现在汇总行里**(`全部通过 · ⚠ N 项告警未拦截(...)`),
> 所以「全部通过」不再是一个可被误读的绝对断言。但**验收命令仍应带全开关**。

> ⚠️ **验收请带全四个开关**:
> ```
> node scripts/verify.ts --all --strict-reach --strict-taut --strict-inert
> ```
> 裸 `verify.ts` 对三道「新增未登记项」只**告警不拦截**。汇总行会自报未拦截项
> (形如 `全部通过 · ⚠ N 项告警**未拦截**(可达性:加 --strict-reach 才算失败)`),
> 所以它不再是一个可被误读的绝对断言 —— 但**带上开关才是真门禁**。

用例总数由验证器**自动汇总**,不靠人工累加 ——
并会检查「通过数 = 总数」,数字不自洽立即报错。

> **口径说明**:上表数字是**用例(test 块)数**,不是 assert 条数 ——
> 每个用例内部通常含多条断言(`eq()` / `ok()` / `includes()`),全仓断言条数
> 是用例数的数倍。**具体条数不在此处写死**:这一句曾写「`WS-07` 有 144 个用例、
> 523 处 `eq()`」,而门禁只校验**表格**、不校验散文 ⇒ 表格每次都同步、散文却
> 悄悄过期(实测已漂到 156 个用例)。手写且无人校验的数字就是**静默口袋**,
> 故删掉具体数字 —— 要看数量级请查上表与套件自己的 `report()` 输出。
> 早期版本把它写成「断言数」,那是**口径失真**:会让人误以为覆盖粒度是断言级。
